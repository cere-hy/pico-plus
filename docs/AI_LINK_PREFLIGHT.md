## 一、send 的非阻塞性（点击路径里直接发 BLE）

**疑点**：`boxsel_ai_send()` 在**手势回调里同步**调 `push_sink_ai_scene_send()`。
若发送内部有等待/重试循环，mbuf 满时会拖住整个主循环（UI 与手势是同一个任务）。

**查证（26.9.27，读码，未改码）**

| 事实 | 位置 |
|---|---|
| 入口做四条前置门 + 参数检查后即 `lock()`（`xSemaphoreTake(s_lock, portMAX_DELAY)`） | `components/push_sink/src/push_sink.c:2474`、`:297` |
| 临界区内是**有界**的：`push_scene_frame_count()` 定帧数（≤5，由 1024 B 上限推出），每帧一次编码 + 一次 `notify_status()` | `:2499-2517` |
| `notify_status()` 无等待：`ble_hs_mbuf_from_flat()` 失败**立刻返回 false**，`ble_gatts_notify_custom()` 直接返回 rc；**重试不在调用方线程内做**——`notify_retry_schedule()` 起一个 100 ms 的一次性 esp_timer，跑在 timer 任务里 | `:559-582`、`:503-523` |
| 循环条件是 `i < total && ok`：任一阵失败即整条中止，**没有 while 重试** | `:2501` |
| `push_sink_ai_scene_send()` 自身**不调** `ensure_init()`（同文件 2339-2426 的邻居入口都调） | 依赖 `app_main.c:278` 的 `push_sink_init()` 先行 |

**显式结账（三格，一格空着就算没结 —— 检查单项最安静的死法是既不做也不划掉）**

| 口径 | 状态 | 结论 / 证据 |
|---|---|---|
| 静态：点击路径有没有无界等待或重试 | **✓ 已查证（26.9.27 读码，未改码）** | 没有 `while` 重试（循环条件 `i < total && ok`，任一阵失败即中止）、没有 sleep、没有 `portMAX_DELAY` 之外的无界项；唯一无界项是 `s_lock`，持有者全是 push_sink 自己的短临界区。mbuf 满时 `ble_hs_mbuf_from_flat()` 立刻返回 false，重试由 `notify_retry_schedule()` 丢到 100 ms 一次性 **esp_timer**（timer 任务里跑），不占调用方线程 |
| 动态：真机「点击 → 页脚回执」时延 | **✗ 待办（放开 y 前必做）** | 未测。目标 ≤50 ms（`guard_draw` 时间戳或 P99 打点）；若明显更长，**改走家务片**——缓冲是静态的，迁移不改会话语义 |
| 代码：`push_sink_ai_scene_send()` 的初始化依赖 | **✗ 待办（放开 y 前必做）** | 该入口自己不调 `ensure_init()`，靠 `app_main.c:278` 的调用顺序活着；顺序一改，`xSemaphoreTake(NULL, …)` 当场崩。补**防御性 init**（`ensure_init();`，幂等）**或断言**——**不接受只加一条注释**：注释维持的契约，reorder 一次就无声破 |

**静态结论**：保持现状（点击内同步发）。理由是会话语义简单——一次点击 = 一次完整的
seq/total 序列；移进家务片反而要维护「发到一半被打断」的状态。这个结论**只覆盖静态面**，
不覆盖上表后两格。

## 二、按键路径能否触达 AI 键

**疑点**：置灰挡下落在 `boxsel_touch` 层；若实体键也能「确认」动作栏，置灰就只是装饰。

**查证（26.9.27，读码）**

- `on_key()`：`if (boxsel_active()) { boxsel_exit(BOXSEL_EXIT_KEY); … return; }` ——
  框选态下任何实体键只做一件事：**关框选**。动作栏的三个键在按键路径上不可达。
- `on_key_long()`：同样只 `boxsel_exit(BOXSEL_EXIT_KEY_LONG)`。

**结论**：不存在按键触达路径。**不需要在 B34 里加「按键也要判置灰」的条款**，
但要防它将来被加进来——已加**静态牙**：

> B34 ④（S26-4）：`on_key` / `on_key_long` 的函数体里不许出现 `boxsel_action(`。
> 假违规已验：在 `on_key` 里插 `boxsel_action(0)` → 咬。

## 三、单槽回执的积压场景

**疑点**：回执只有一个槽。y 放开后，「队列有积压 + 点 AI + 同一拍冲账成功」时，
`已存 ✓` 会顶掉 `未发送`——这不是窄窗口，是积压场景的常态。

**裁决：采纳异常优先（26.9.27 已落码，不等 y）**

- `excerpt_hint_set(text, cls)` 两参数；`EXCERPT_HINT_ALERT` 不被 `EXCERPT_HINT_INFO` 顶掉，
  同级别可互相顶掉（最新为准）。
- ALERT：`未发送` / `摘抄已满` / `内存不足` / `[截] 已按上限摘录` / `无选中文本`
- INFO：`已存 ✓` / `AI 已发`
- 牙：B37（每个调用点必须带等级；两类文本的归档必须正确；设置函数必须真的实现优先规则）。

**为什么不等 y 再改**：这个碰撞在 **n 口径下已经能撞上**——摘一条超长文本
（`[截]` 是 ALERT）+ 同一拍里积压冲账成功（`已存 ✓` 是 INFO）。y 只是让它更常见。
一个只有 y 才成立的理由，抵不过一个今天就在发生的事实。

**代价（照实说）**：超长摘录那条，「`已存 ✓`」会被 `[截]` 顶掉，用户看到的是
`[截] 已按上限摘录 · 待落盘 0 · …`。落盘事实没丢——**待落盘归零就是证据**；
且 `[截]` 本来就是他要处理的事。翻页后回执按页作废，槽位自然清空。
