## 四、**待裁点 1**：release 重试，`s_release_pending` 是否该继续置 false

这是全批唯一需要人判的地方，两侧都有实测支撑：

| 侧 | 主张 | 依据 |
|---|---|---|
| 31b | 三次失败 → `s_release_pending = false` + `hold` 留痕 + 放弃卸载 | 「无限静默冻结」是三拍要防的东西，必须留痕 |
| 31a | 三次失败 → 继续卸（10 s 节拍）**永不放弃** | 放弃卸载 → `card` 永远非空 → `mount_card()` 全以 `stale card` 拒绝 = 环④，「插回不认卡、只能重启」的第二个入口 |

**执行侧的解（已落码，供裁）**：拆成两层，因为它们说的是两件事。

- **卸载动作**永不放弁（取 31a）：卸载失败 = 卷还挂着，唯一出路是继续卸。
- **push 冻结**在跨过 fast 档那一刻 `hold` 留痕一次（取 31b），此后每 6 次重复一句。
- `hold` 是**留痕**不是终态：卸载一成功，上面的 `push_sink_thaw()` 照常解冻（31b 终态①不变）。
- 唯一的实质差别：`s_release_pending` **不再置 false**。

**理由**：31b 置 false 的语义是「放弃卸载」，而 31a 已用现场证明放弃卸载才是那个死锁。
「无限冻结」的代价改由 hold 留痕 + 周期日志承担——**冻结是暂时的，且说得出为什么**。
若审计认为"冻结不得超过 N 次"必须硬性成立，则需另立一条兜底（例如第 30 次失败强制
`s_release_pending = false` + 上报），请裁。

## 五、两处**实测**修正（都不是推断）

### ① 桩码漂移（§13.12a 靶子为假）

合流时我先"推"了一个结论：P1-1 判死用 `NOT_FOUND`，`app_loop` 兜底写的是
`err != ESP_ERR_NOT_FOUND`，所以判死后没人再碰这张卡 → 把判死码改成 `TIMEOUT`。

改完一跑，`sd_probe` 打印 `gi=259`——**259 是 INVALID_STATE**。真相：判死后的下一次
`get_info()` 会走 `observe_media_locked()`，那里在锁存期把快照整体重写成
`{present=1, mounted=0, error=INVALID_STATE}`（31a 环③的修法）。**判死码根本不决定看门狗入口**。

真正的偏差在**宿主桩**：桩 `return ESP_ERR_NOT_FOUND`，真件返回 `INVALID_STATE`。差一个码，
`app_loop` 兜底分支就被跳过——「判死之后还有没有人碰这张卡」这条路径**在宿主侧从未被走到**。
桩已按真件改正，判死码保持原样。

判据本身也纠正了：看门狗在 app 侧叫 **`start_probe`**，不叫 `remount`（实测 14:1）。
断言因此写成 `probes >= 2`——咬的是「判死后还有人碰这张卡」，不是「码是多少」。

### ② `epoch_steps[8]` 装不下 16 拍

P1-1 场景从 4 拍扩到 16 拍（看门狗第一档 8 s），ASAN 当场报 `global-buffer-overflow`。
扩到 32 格。**改测试窗口忘了改桩数组**，这条记进测试自身的坑。
