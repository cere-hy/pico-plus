## KI-001 · `settings_entry_clock_host_test.py` 编译失败（宿主桩陈旧）

| 项 | 内容 |
|---|---|
| 状态 | **挂账（OPEN）** — 不阻塞 26.9.11 及后续补丁版出包 |
| 首次发现 | 2026-10-29，26.9.11 可复现构建后的全量门禁回归 |
| 定责 | 历史测试债，与 M5-A 框选、生词本收口**无关** |
| 裁定 | 2026-10-29 审计端裁定：挂账，另开工单，随宿主测试桩统一重构一并清理 |

### 现象

实测输出（2026-10-29 复跑，节选；`-Werror` 下全部升级为错误）：

```
test.c:117:5:  error: implicit declaration of function 'ui_fill_rect_fast'
test.c:167:51: error: 's_next_generation' undeclared (first use in this function)
test.c:167:72: error: implicit declaration of function 'book_layout_generation'
test.c:168:20: error: implicit declaration of function 'reader_prefetch_resume'
test.c:171:9:  error: implicit declaration of function 'draw_reader_outer';
                      did you mean 'draw_reader'?
test.c:105:13: error: 'epd_fill_rect' defined but not used
cc1: all warnings being treated as errors
```

宿主测试桩在编译 `main/apps/app_book.c` 时缺少 `.c` 里新增的一组声明
（`ui_fill_rect_fast`、`s_next_generation`、`book_layout_generation()`、
`reader_prefetch_resume()`、`draw_reader_outer()`），外加一处桩自身
「定义但未使用」的函数（`epd_fill_rect`）。**共 6 条，全部是编译期缺桩，
不含任何运行期断言失败** —— 也就是说这个测试目前根本没跑到断言那一步，
它的"绿"是不可信的，这也是为什么必须整桩重构而不是逐条打补丁。

### 关键证据：与本轮改动无关

在**改动前的提交 `5650e21`**（26.9.11 第一版，早于可复现构建提交 `944886e`）
用独立 worktree 复现：

```
$ git worktree add --detach /tmp/head_tree 5650e21
$ cd /tmp/head_tree && python3 tools/settings_entry_clock_host_test.py
→ 同一个编译错误
```

即：该红在可复现构建改造之前就已存在，属存量债。

### 根因

`tools/settings_entry_clock_host_test.py` 用「把被测 `.c` 一起编译 + 手写桩 stub 掉
其外部依赖」的方式做宿主测试。桩文件是**逐次手写**的，`app_book.c` 每长出一个新的
跨文件符号，桩不会自动跟上——一旦漏掉，就是编译期硬失败，而非运行期软失败。

同批测试里 `tools/input_editors_host_test.py`（同样编译 `app_device_settings.c`）
**通过**，说明骨架本身可用，缺的只是 `app_book.c` 这一路的桩补齐。

### 为什么当时没有顺手修

1. 该测试的测试对象是「设置页时钟入口」，与 `app_book.c` 的阅读区绘制完全不在一条路径上；
2. 为让它编译通过，需要给 `book_layout` / 阅读区绘制补一批桩，属于**重构宿主测试桩**的
   范畴，不是一处小补丁；
3. 代码端不得在未审的情况下顺手改测试结构（会污染本轮的「门禁全绿」结论）。

### 清理方案（待后续统一重构时执行）

- 触发条件：下一次宿主测试桩统一重构 / `app_book.c` 再有跨文件符号增长时。
- 方向 A（推荐）：抽出共享桩头文件 `tools/stubs/app_book_stubs.h`，由所有编译
  `app_book.c` 的宿主测试共用，新增符号只补一处。
- 方向 B：把 `settings_entry_clock_host_test.py` 的被测面收窄为
  「时间编辑器的纯逻辑函数」，不再整份编译 `app_book.c`。
- 验收：该测试编译通过并全绿，本条目改为 CLOSED，同时在 `RELEASE_NOTES` 里记一笔。

## KI-002 · P0-a「6 KB prep 栈切碎内部堆」假设证伪（CLOSED）

| 项 | 内容 |
|---|---|
| 状态 | **已结案（CLOSED）** — 2026-10-29，26.9.13 真机日志判读后 |
| 首次提出 | 26.9.12 真机诊断：开书瞬间内部最大块 21,504 → 14,336，差值 7,168 ≈ 6,144 栈 + 1,024 TCB |
| 原方案 | 把 prep 栈搬进 PSRAM（`CONFIG_BOOK_PREP_STACK_PSRAM`），26.9.13 已预置开关、默认关 |
| 裁定 | 审计端 2026-10-29：**坚决结案，永不启用**。代码保留、开关仍 `default n` |

### 证伪证据（`gen26.9.13.txt`）

```
I (75153) book: close before internal free=59871 largest=13312
I (75163) book: prep stack HWM: 3412 B free (peak used 2732 B) of 6144 B stack
I (75163) book: prep task stopped (close): 6K stack returned
I (75359) book: close after  internal free=66763 largest=18432   ← +6,892，栈确实归还
I (101772) 首次 ble-start：internal free=67239 largest=18432     ← 起 BLE 时它早已不在场
```

自删路径正常工作，栈在关书时回到内部堆并参与合并（largest 13,312 → 18,432）。
起 BLE 发生在 101,772（关书之后 26 s），free 已是 67,239 —— **搬走那 6 KB，largest 也不会涨**。

### 真正的病灶（改由 26.9.14 A 档处理）

开机一次注定失败的离线对时（`esp_wifi_init` 16,301 ms → 超时 teardown 31,405 ms，正好 15,104 ms）
把 32,767 B 的池切成 5 段：30,935 B 空闲 / 最大块 18,432 / 11 个约 96 B 残块 / `min_free=0`。
详见 `26.9.13-真机战报与P0-e方案-20261029.md`。

### 遗留价值

`prep stack HWM` 那行白捡了一个事实：**6,144 B 的栈峰值只用 2,732 B（44% 水位）**。
将来若真要省这 6 KB，**缩栈**比搬 PSRAM 便宜（无 cache 关闭窗口风险）。本条只记录，不触发动作。

## KI-003 · TF 卡热插拔永远认不出（CLOSED）

| 项 | 内容 |
|---|---|
| 状态 | **已结案（CLOSED）** — 2026-10-29，26.9.17 落码，当晚真机三轮连击全部恢复（`gen26.9.17.txt`：83 条读失败 → 每轮 2 条、词典可重开、`books=7 roots=2` 三次） |
| 首次提出 | 26.9.16 真机反馈：开机插着卡能读，拔出来再插回去永远认不出，必须重启 |
| 影响 | 功能阻断。用户换卡/取卡后整个书库、词典、字体都不可用，只能重启 |
| 定责 | 两层历史缺陷叠加，**非 26.9.16 引入**；26.9.16 只是把第二层的门焊死了 |

### 病灶（两层，互为表里）

**第一层：拔卡没有卸载。** `esp_vfs_fat_sdcard_unmount()` 只在 `close_card()` 里被调，
`close_card()` 只被 `read_pico_sd_remount()` / `read_pico_sd_sync()` 调；主循环的 lost 分支
两个都不调。FAT 卷、pdrv、VFS 挂载点、SDMMC host 全部保留。

**第二层：插回被自己的门锁住。** `app_loop.c` 的兜底探测条件 `… && !*invalidated`
构不成出路：`*invalidated` 只由 `ready` 清，`ready` 要 `mounted`，`mounted` 要探测，
探测要 `!*invalidated`。

### 铁证（`gen26.9.16.txt`）

```
53.47 s  sd: err=ESP_ERR_NOT_FOUND present=0 mounted=0 invalidated=0   ← 拔卡，检测正常
54.40 s  sd: … invalidated=1                                            ← lost 已通知，未卸载
64.81 s  sd: err=ESP_ERR_INVALID_STATE present=1 mounted=0 invalidated=1 ← 插回已捕获，探测被挡
131.95 s 串口关闭
```

- 全程 `sd: probe start` **0 条**、`sd: remount` **0 条**
- `dict: opendir /sdcard/dict errno=5 (EIO)`（26.9.15 同位置是 `errno=2`，ENOENT）
- 拔卡后 **83 条** `sdmmc_read_blocks failed (0x107)` @sector 16386

### 修法

26.9.17 T1（lost 分支调 `read_pico_sd_remount()`，拔卡状态下只 unmount 不探测）+
T2（去掉 `!*invalidated`）+ T3（`mount_card` 拒绝对非空 `card` 假成功）。
门禁 `tools/check_hotplug.py` K1–K5，变异 M52–M57 全擒。

### 遗留风险（已知未修）

BLE 推送（`push_sink`）正在写卡时拔卡，理论上有悬空句柄风险。审计裁定本版直接上、
崩了再补。若真机出现卸载后崩溃，26.9.18 补 `push_sink` 的 lost 回调。

## KI-005 · 池 A 稳态最大块已跌破 26.9.13 定的蓝牙闸门（CLOSED：6,144 已销号，余额转 KI-007）

| 项 | 内容 |
|---|---|
| 状态 | **CLOSED（2026-10-30 审计裁定销号）** — 6,144 这笔由 26.9.19 S8 销掉；剩余那笔 1,024 转 KI-007 挂账 |
| 首次量到 | 26.9.17 真机（`gen26.9.17.txt`），但当时没人意识到那是个问题 |
| 影响 | 若 19,456 打不开蓝牙，则用户"开词典 + 开过书 + 拔插过卡"之后就无法传书 |
| 定责 | 不是回归，是**账本第一次被完整量到**；两笔各 1,024 B，都是老账 |

### 账本

```
21,504   开机（池 A 无碎片天花板，boot-pre / boot-post 两次完全相同）
−1,024   词典块缓冲（`dict: opened … block_log2=10`，首次打开后常驻不退）
=20,480  ← 26.9.13 结案时写的"闸门值，余量为 0"
−1,024   开书清场（`open start` 之后 1 ms 内掉，关书后退不回来）
=19,456  ← 26.9.17 实测稳态，三轮拔插前后一动不动
```

**三轮热插拔本身不泄漏**（20,480 → 20,480 → 20,480 → 19,456，最后一次下降发生在开书，
不在拔插）。所以 26.9.17 的 T1 是干净的，这条与它无关。

### 为什么当时算错了

26.9.14 那笔账是从 `boot-pre`（18.6 s）的 21,504 起算的，**而词典 56 s 才打开**。
于是"−1,024 开书"被算成了闸门 20,480，实际那是"开词典之后"的天花板；再开一次书才是 19,456。

### 闸门为什么不能直接下修

26.9.13 的依据是"largest 18,432 时蓝牙开不了"。19,456 落在 18,432 和 20,480 之间，
**没有任何实测数据**。现在下修等于把闸门改到一条没验证过的位置上。

### 处置

26.9.18 已把黑匣子重开（50 ms 采样、逐段 delta），并安排真机按
「开词典 → 开书 → 关书 → 拔插三轮 → 开蓝牙」走一遍：

- **能开** → 闸门下修到 19,456，本条目 CLOSED；
- **开不了** → 26.9.19 回收两块 1 KB（词典块缓冲改按需分配、开书清场改栈），本条目转为修复项。

### 26.9.18 真机结果：**账本整个重写**

`gen26.9.18.txt` 的 `boot-post` 块表（47.3 s，开书之后）把真身钉死了：

```
Block 0x3fccfb64  size: 6144 bytes, Free: No     ← book_prep 任务栈
Block 0x3fcd1368  size:  100 bytes, Free: No     ← 夹在中间的 100 B，合并杀手
Block 0x3fcd13d0  size: 13632 bytes, Free: Yes   ← 全堆唯一的大空闲块 → largest 13,312
```

**"两块 1 KB"作废。** 真实账本是

```
21,504  开机
−1,024  → 20,480（t=26.1 s；26.9.17 归给词典，但词典 27.3 s 才开，归因存疑）
−1,024  → 19,456（t=32.25 s，开书前 1.2 s，未归因）
−6,144  → 13,312（book_prep 栈：峰值只用 2,788 B / 45%）
         ↑ 此后 100 s 一动不动，开书/关书/拔插/蓝牙都不改
```

**关书为什么不恢复**：6,144 归还后，它的两个邻居里只有一个是空闲块（13,632 在 100 B 块之后，
不相邻），FreeRTOS 不合并，只多出一个 6,144 的洞。`MEM_HEALTH_RED_BELOW = 15,360`，
于是面板长期显示"内存不足，请重启设备"——而重启再开一次书就回到 13,312。

**蓝牙那条判据同时作废**：26.9.18 真机上蓝牙是走 `heapdiag: site=push-bypass largest=13312`
开起来的——闸门 20,480 必然拒绝，它绕过去了。"19,456 能不能开蓝牙"这个问法本身有问题。

### 26.9.19 处置（审计裁定）

- **S8**：`CONFIG_BOOK_PREP_STACK_PSRAM=y`，6,144 B 栈搬进 PSRAM，池 A 从构造上不再付这笔钱。
  审计同时**推翻 26.9.13 的"永不启用"**（当年理由"有风险且没到绝境"已不成立）。
  回滚条件：cache 关闭窗口（NVS 提交 / OTA 写 flash）崩溃 → 改走缩栈 (b) 6,144 → 3,584。
- **验收判据**：`book: open start … largest=` 从 13,312 回到 **19,456 左右**（多出这 6,144）、
  内存面板不再报红、拔插三轮不退化、蓝牙在阅读态能重新打开。
  **19,456 仍低于闸门 20,480，所以 `push-bypass` 出现属预期**——闸门放行要等那两笔各
  1,024 B 也归因之后（26.9.20）。
- 状态仍是 **OPEN**，等 26.9.19 真机。

### 26.9.19 真机结果：**6,144 的悬崖没了，但只回到 19,456**

`gen26.9.19.txt`（478 s）逐点核对：

| 时点 | 26.9.18 | 26.9.19 |
|---|---|---|
| 首次 `open start` | 20,480 | 20,480 |
| 第二次 `open start` | **13,312** | **19,456** |
| 全程出现 13,312 | 是，永久 | **一次都没有** |

差的那 6,144 B 就是 S8。**但面板只到「黄」，到不了「绿」**：绿线 20,480 来自 BLE 闸门，
而按账本本版最好就是 19,456，还差 1,024。所以 26.9.19 README 里写的「从红变绿」是错的，
实测只能是「从红变黄（内存偏紧，建议退出阅读）」。红灯确实消失。

**蓝牙那条判据本身也是失效的**：`push gate skipped: stack already up`——NIMBLE 栈从开机
就起着，闸门压根不会被查询，与 largest 是 13,312 还是 19,456 无关。要测闸门必须冷启动、
全程不碰翻页器。已单列为 26.9.20 的独立测试项。

**状态**：6,144 这一笔 CLOSED，**26.9.21 出包时按审计裁定正式销号**（14 次采样峰值 2,912 B、
不崩，S8 这条不再作为风险项挂着）；剩下的 1,024 由 KI-007 接管并改判为「每 boot 一次」；
闸门值仍按住不动（26.9.21 S18 已把面板绿线删掉，闸门不再作为面板判据）。

## KI-007 · 池 A 最大块每 boot 少 1,024 B 一次（CLOSED：2026-10-30 审计裁定销号）

| 项 | 内容 |
|---|---|
| 状态 | **CLOSED（2026-10-30 审计裁定销号）** — 26.9.24 真机终验满足全部三条判据，见下 |
| 首次量到 | 26.9.19 真机（`gen26.9.19.txt`），把 26.9.18 账本里两笔「未归因的 1,024」钉成了同一件事 |
| 影响 | 第 7 次开书跌破面板红线 15,360——**这条推论随改判一起作废**，见下 |
| 旧判据 | 每次开书都掉 1,024（26.9.20 数据证明这是错的） |

### 账本（旧，已被 26.9.20 推翻）

```
20,480 →(开书1) 19,456 →(开书2) 18,432 →(开书3) 17,408 → …
```

26.9.20 的 10 次开书里 `delta=-1024` **只出现两次：第 1 次和第 8 次**。第 8 次不是
「第 8 次开书」，而是**重启后的第一本**——同一个日志文件里有两段 boot，第 2 段的第一本
又掉了一次。把它读成「第 8 次开书」会把一次性开销误判成线性泄漏；正确读法是
**每 boot 一次**。

### 26.9.20 处置：五个路标（已交付，数据到手）

`pico_heap_mark()` 沿开书路径摆五处（`reserve1` / `save` / `free` / `font` / `reserve2`），
每行给 `free / largest / blocks=free/alloc / delta=`。相邻两行的 `delta=` 直接点名。
**26.9.20 不加修复**——「先归因后动刀」仍然适用。

### 26.9.21 处置：不修，只把判据改对、把观察窗拉长到 20 连开

改判不等于销号。一次性 1,024 与线性泄漏的区别**只能靠次数拉开**：10 次开书只够看出
「不是每次」，不够看出「会不会慢慢积累」。26.9.21 的判据因此写成两条：

1. `delta=-1024` **只应出现在每个 boot 的第一次开书**；
2. `largest` 会在 16,384 / 15,872 之间 −512/+512 成对摆动（块分裂），**不许一路沉降**。

若 20 连开后 `largest` 仍停在 16,384 上下摆动 → 确认为一次性开销，届时销号；
若出现第三个 `-1024` 或跌破 15,360 → 判为线性泄漏，回滚级缺陷。

### 26.9.21 真机：24 次开书，`-1,024` 一次都没出现——**仍然不能销号**

`gen26.9.21a.txt` 的 24 次开书，`delta` 全是 `+0`。看着像修好了，其实不是：

**总账先掉到 14,336 了。** S14(b) 那块 8 KB 堆缓冲每次插卡切一刀，`largest` 从 18,432
掉到 14,336 并再也不回——**一个 1,024 的坑被一个 4,096 的坑盖住了**。坑在不同深度，
下面那个还漏不漏，这个观察窗看不见。

审计 26.9.20 的裁定「改判但先别销号」因此继续有效，判据追加一条：

3. **必须在 `largest` ≥ 16,384 的前提下采集**。总账低于 16,384 时，`-1,024` 可能被
   更大的空洞吸收，`delta=+0` 不构成"没有泄漏"的证据。

26.9.22 把缓冲搬进 `.bss`，就是为了把观察窗抬回 18,432 再验一次。

### 26.9.24 真机终验（销号依据）

`gen26.9.24.txt`：B2 闸门两层化后稳态 `largest` 在 16,384/17,408（判据 3 的前提成立），
3 次传书 + 23 次开书 + 5.2 分钟长跑，`delta=-1024` **零次出现**（判据 1）、无沉降
（判据 2）、主堆 min_free 终值 10,928。审计批复原话：「持续数天的内存泄漏阴霾正式
散去」。历史教训归档：本条从「每次开书掉 1,024」的误读到「每 boot 一次」的改判，再到
观察窗被 8 KB 缓冲坑盖住又挖开，前后跨 26.9.18–26.9.24 七个版本——**归因比修复慢，
是这类账目的常态，判据先行能少走弯路**。

## KI-008 · `boot-post` 块表里的 8,192 B 常驻块（归因完成：**`nimble_host`**；修复 OPEN）

| 项 | 内容 |
|---|---|
| 状态 | **归因 CLOSED，修复 OPEN**（26.9.21 记入；26.9.20 埋的点在真机上对上了） |
| 首次量到 | 26.9.18 / 26.9.19 真机的 `boot-post` 逐块表 |
| 归属 | **`nimble_host` 任务栈**，`pxStackBase = 0x3fccea8c`，与块表地址**逐字节相同**；HWM **6,084 / 8,192（74%）** |
| 影响 | **「合并杀手」**：后面紧跟一个 100 B 常驻块，把 21,564 B 的空闲块一切两半。只要它在，largest 就上不了 20,480 |
| 形态 | `Block 0x3fccd454 size: 8192 bytes, Free: No` → `Block 0x3fccf458 size: 100 bytes` → `Block 0x3fccf4e4 size: 21564 bytes, Free: Yes` |

### 26.9.20 埋点 → 26.9.21 结案

`CONFIG_FREERTOS_USE_TRACE_FACILITY=y` + `pico_heap_attr()` 反查每个 `pxStackBase` 的真实块
大小。真机 `gen26.9.20.txt` t=83.2 s 的 11 个任务里，只有两个栈基址与块表**逐地址**相同：

| 块地址 | 大小 | 任务 | HWM |
|---|---:|---|---:|
| `0x3fcc8b74` | 12,800 | `main` | 4,124 |
| `0x3fccea8c` | **8,192** | **`nimble_host`** | **6,084（74%）** |

`0x3fce0c50` 的 8,800 B 仍无主（不在任务栈列表里），三处 4,096 只做到"大小相同"、
未逐地址核对——**不冒充结论**。

**结论：它不是泄漏、不是碎片残留，是蓝牙协议栈任务栈。**

### 为什么修复还挂着

8,192 是 `CONFIG_BT_NIMBLE_HOST_TASK_STACK_SIZE`，占用 74%，**缩栈等于拿运行期崩溃换
1 KB**，必须有 HWM 的长时数据才敢动；"使用时才起栈"要改 `ble_pt_sync()` 的常开语义。
两条都不是本版范围。

### 26.9.21 的处置：把它从判据里摘出去

既然 8,192 动不了、闸门又在用户路径不可达，**面板绿线就永远点不亮**。26.9.21 S18 按
审计裁定 ① 删掉绿线（只留红 <15,360 / 黄 ≥15,360），裁定 ③ 把闸门收窄到自检态。
**这不等于 KI-008 不重要**——它仍然是让 largest 上不去的那块石头，只是不再拿它当
"用户体检指标"。

**26.9.24 交叉引用（B1 结案）**：B1 cut-who 块表把 t≈3.9s / t≈36.8s 两刀的账都归到
BLE 启动刚需（`btController` 栈 4,096 + NimBLE 主机池），与 KI-008 的 8,192 常驻块
同源同性质——**审计 2026-10-30 裁定 B1 结案，排除漏内存嫌疑**。本条维持「接受现状」
口径不变。

## KI-009 · 开书内联图单次 `esp_jpeg_decode` 占 CPU0 超 5 s，IDLE0 饿到触发 task_wdt（S25 已修，待真机复发验证）

| 项 | 内容 |
|---|---|
| 状态 | **OPEN（S25 已缓解未根治）** — 26.9.25 真机：预算生效但超大图单次解码仍 >5 s，见下 |
| 首次量到 | 26.9.24 真机 `gen26.9.24.txt` t=190.3 s，唯一一次 |
| 现象 | `task_wdt: IDLE0 (CPU 0)` 未喂狗；开书最终成功（413 ms draw）、无崩，属长阻塞 CPU 饥饿，非死锁 |
| 根因 | backtrace 按 26.9.24 ELF 逐帧落名：`esp_jpeg_decode`（jpeg_decoder.c:113）← `jpeg_gray` ← `prepare_inline_image`（app_book.c:4921）。该调用是单个库函数，**内部无法让出**；`prepare_inline_image` 每图 `vTaskDelay(1)` 与软解/PNG 的行级 `decode_yield` 都救不了它 |
| 量化 | 解码预算上限 6 MB RGB565（≈3 M 像素），耗时 ∝ 输出字节，单次可 >5 s（wdt 阈值） |

### S25 修复（26.9.25 已出包）

`book_image_grayscale` 增加 `max_out_bytes` 预算参数（0 = 内置 3/6 MB 规则不变）；
**插图路径传 2 MB**——单次解码压到 ≈2 s（3× 余量）；封面/锁屏拼贴/TF 图片传 0，
行为不变。插图最终只显示页宽，预算收紧质量无损。

### 销号判据（26.9.25 真机）

1. 重开同一本大图书（或任意含大插图章节），日志**不得**再出现
   `task_wdt: Task watchdog got triggered`；
2. 插图照常显示，`grayscale decode failed` 无新增；
3. 传书 2 次仍 `verify ok`、书架 ≈1.1 s（温故）。

### 26.9.25 真机复核：主判据未过——S25 假设证伪（自曝第 4 条，2026-10-30）

`gen26.9.25.txt`：WDT 两次（t=104.2 s 翻页预载 / t=127.1 s 开书），backtrace 仍是
`esp_jpeg_decode ← jpeg_gray(book_cover.c:278) ← prepare_inline_image` 同一条链。
S25 的 2 MB 预算**确认生效**（帧地址全部落在 26.9.25 新代码位），但单次解码仍 >5 s。
根因修正：esp_new_jpeg 的 **Huffman 熵解码 ∝ 输入全图像素，`out_scale` 只缩 IDCT
输出**——"耗时 ∝ 输出字节"是错的，输出预算对超大输入图（估 12 MP 级）无效；
JPEG 也无法只解码局部。S25 对中小图仍然有效（大批插图因此更快），但恰对最毒的
那张大图无效。设备两次 WDT 后继续正常运行，无崩无重启。

用户表态：「那只是个封面，划过去就好了，感觉只是卡了一下」——定级"可接受的卡顿"。
26.9.26 三个方向（AC-004 接受现状 / S26a 摘 IDLE0 出 wdt / S26b 解码挪出主任务）
已提请审计裁决，见 `26.9.25-真机判读与26.9.26方向-待审-20261030.md`。
