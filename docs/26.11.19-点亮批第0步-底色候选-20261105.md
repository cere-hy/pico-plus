## 一、要查的不是「这页多白」，是「差刷填什么色」

读码给出一条容易搞反的分工：

```c
// app_loop.c:297-300（差刷路径）
ui_fill_rect_fast(area, (uint8_t)bg, ctx->fb);   // ① 先按 bg 填这块区域
ui_nav_status(ctx->fb);                          // ② 再画时间/电量/图标
update_display_area_diff_with(...);
```

- **`bg` 来自 `app_desc_t.status_bar_bg`**（`app.h:134`；`app_loop.c:279` 取值，NULL → -1 → 不刷）；
- **页面静态底色来自 `ui_clear_page()` = 全屏 `0xFF`**（`ui_kit.c:1490-1492`）；
- 两者**不必相等，但必须视觉一致**——差刷一次就把 `bg` 永久写进那块区域，与周围产生色斑。

所以第 0 步的问题精确化为：**每页的 `status_bar_bg` 该返回什么，才能和该页条带的静态底色一致。**

## 二、已知值表

| 值 | 语义 | 出处 | 用在 |
|---|---|---|---|
| `0xFF` | 纯白（页面静态底） | `ui_clear_page` memset 0xFF | 绝大多数页 |
| `0xE0` | nibble 14（≈93% 白，仍非纯白） | `ai_reader.h:139-149` | 书架普通档；引用条浅底 |
| `0xF0` | 纯白档（`0xF0+` 归纯白） | 同上注释 | 书架快刷档 |
| `0xEE` | 卡片灰 | `app_dashboard.c:729` `card_gray` | 首页卡片（**不在条带区**） |

**三档设置、两个返回值**：`app_settings_main_refresh_mode()` 有 `NORMAL / FAST / WATER` 三档
（`settings.h:48-50`），而书架的 `status_bar_bg` 只判 `fast ? 0xF0 : 0xE0`——**WATER 与 NORMAL 共用 0xE0**。
默认档是 `NORMAL`（`settings.c:216-217`），所以**默认书架条带差刷色 = 0xE0，而页面静态底是 0xFF**。
真机 A1「整条刷新完美」+ 电量批「书架无色差斑」说明这一档差（nibble 14 vs 15）在 GL16 下**不可见或可接受**。
**WATER 档是否该有第三值：现状无证据，记为待查**（不预设它错，也不预设它对）。

## 三、8 页点亮的前置缺口：不是「查色」，是「先有回调」

`grep -rn "status_bar_bg" main/apps/*.c` 只有两处实现：

| 页 | 回调 | 返回 |
|---|---|---|
| 书架（`app_book.c:10536`） | 有 | `s_view==SHELF && !confirm` → `fast?0xF0:0xE0`，否则 `-1` |
| 首页（`app_dashboard.c:1229`） | 有 | `s_view==HOME_ROOT ? 0xFF : -1` |
| 其余页 | **NULL** | `app_loop.c:279` → `-1` → 整条不刷（连电量也不跟） |

**所以盘点里「6 页连电量也不跟」的机制不是 `-1` 写死的，而是回调根本没接。** 点亮一页 = 三件事：

1. **加 `status_bar_bg` 回调**（回答「条带在不在 / 底色多少」）；
2. **确认该页条带静态底色**（读 render 的 fill 值，见下）；
3. **真机验无斑**（差刷一次后看边界）。

## 四、读码方法（每页一次，可批量）——**v2 修正：原命令会误捕**

原 ③ 命令（`grep -n "ui_fill_rect.*{0,\s*0\|UI_STATUS_STRIP_H\|y.*<.*80"`）实跑复核：

| 判词 | 实测（GNU grep 3.11） |
|---|---|
| 审计说「`{0,` 在 BRE 里是语法错误」 | **不成立**。裸 `{0,` 在 BRE 下是**字面量**，rc=0 正常输出；只有转义形态 `\{0,`（区间语法）缺右括号才 `Unmatched \{` / rc=2 |
| 但命令确实是坏的 | **坏在误捕**：`y.*<.*80` 把 `app_book.c:7967` 的 `s_reader_panel = y < 580` 捕进来了——它和状态栏毫无关系 |

**误捕比语法错危险**：语法错当场报错，误捕静默污染候选表。这是纪律 15「可复算」的准确含义——
不是「命令能跑」，是「跑出来的每一行都该在表里」。

修正后四条（③④ 实跑输出附后）：

```bash
# ① 该页有哪些 render 入口会画状态栏
grep -n "ui_nav_status(fb)" main/apps/<page>.c
# ② 每个入口清屏用什么色（决定静态底）
sed -n '<line-3>,<line+3>p' main/apps/<page>.c
# ③ 条带区是否有专门填充 —— 用单源常量找，不用字面 80
#    （26.11.18 把 UI_STATUS_STRIP_H 单源化，grep 它就是全量，这是节拍批给点亮批的现成红利）
#    注意必须带 *.h：定义与派生都在 ui_nav_layout.h，只扫 *.c 会漏掉它们
grep -rnE "UI_STATUS_STRIP_H|UI_STATUS_GESTURE_H" --include=*.c --include=*.h main/

# ④ 全屏/矩形填充（-E + 花括号转义；只认左上游为 0,0 的整块填充）
grep -rnE "ui_fill_rect[^;]*\{ *0 *, *0 *," --include=*.c main/apps/<page>.c
```

**③ 实跑输出（当前的全体，2026-11-05 复跑，6 行）**：

```

main/apps/app_book.c:5054    static EpdRect reader_status_area(void) { ... UI_STATUS_STRIP_H } ← 阅读器 opt out
main/apps/home_gesture.h:63  /// 高度不再写字面 88，用 `UI_STATUS_GESTURE_H` …                ← 注释
main/apps/home_gesture.h:71  #define HOME_RESERVED_INFO ((EpdRect){0,0,684,UI_STATUS_GESTURE_H}) ← 手势命中区，非填充
main/ui/ui_nav_layout.h:13   #define UI_STATUS_STRIP_H 80                                    ← 定义
main/ui/ui_nav_layout.h:20   #define UI_STATUS_GESTURE_H (UI_STATUS_STRIP_H + 8)             ← 派生

> **两处修正（v3）**：① 原命令只有 `--include=*.c`，产不出 `.h` 的两行——**命令与输出必须成对**，
> 改命令而非删输出；② 原记录只列 4 行，复跑是 6 行——漏的是 `home_gesture.h` 两行（26.11.17 手势批后新增）。
> 这两行**不进底色候选表**：一个是注释、一个是命中区（`HOME_RESERVED_INFO`），**都不是填充调用**。
> 判读时按「填充调用」过滤，而不是按「出现常量」计数——否则会把命中区误当底色来源。

**④ 实跑输出（书架的条带区填充现形）**：

```
main/apps/app_book.c:5010      ui_fill_rect_fast((EpdRect){0, 0, UI_LOCK_WIDTH, UI_NAV_TOP}, ...)   ← 高 UI_NAV_TOP，非条带
main/apps/app_dashboard.c:855  ...ui_fill_rect_fast((EpdRect){0,0,UI_LOCK_WIDTH,UI_LOCK_HEIGHT},0xff,fb) ← 全屏 0xff

**判读规则（v2 补第 ② 条）**：

1. 若入口前只有 `ui_clear_page`（0xFF）、条带区无专门填充 → 候选 `0xFF`；
2. **条带填充查找必须以 `UI_STATUS_STRIP_H` 的引用点为准**——不要再按字面 `80` 找。
   26.11.18 刚把这个常量单源化，此后「谁画整条」只需 grep 一个符号；用字面 80 会同时漏掉
   将来改用 `UI_STATUS_GESTURE_H` 的调用点、又误捕无关的数值比较；
3. 若条带区有独立填充 → 取该值；若页面受设置档影响 → 按档返回（如书架）。

## 五、真机查「有无第二档」（不可省）

## 六、开工包形态

**先记一笔正向收益**（这一点决定了「点亮」的性价比）：

一页点亮 = **补回调 + 定底色**，仅此两件。补上回调后，`app_desc_t.self_clock_tick` 缺省为 `false`，
`app_loop` 的分钟分支条件 `(self_clock_tick || bg < 0)` 自动成立 → **该页自动获得分钟节拍**，
同时电量跟变也跟着来（同一处 `nav_watch_step`）。**一次开工同时吃到 26.11.17（导航条带 / 电量）
与 26.11.18（分钟节拍）两批的机制**，逐页对表时把这一层写在「可开」理由里。

**对表**，成熟一个开一个：

| 页 | 回调已接 | 静态底候选 | 真机档数 | 无斑 | **无斑证据载体** | 可开 |
|---|---|---|---|---|---|---|
| 书架 | ✅ | 0xE0 / 0xF0 | 已知 2 | ✅ | 照片（26.11.15/16 双会话） | 已开（26.11.18） |
| 首页 | ✅ | 0xFF | 待记 | ✅ | 照片（电量批验收格） | 已开（自家 tick） |
| …（8 页） | ❌ | 待读 | 待记 | 待验 | **待定** | 逐页 |

**「无斑证据载体」是 v2 新增列，不是装饰**：「真机验无斑」是**否定性观测**，8 页全靠口头
会原样重演 S2（观测设施清单：否定性观测缺日志载体，照片拍不出「没发生」）。每页至少要留一种载体：

| 载体 | 可行性 | 说明 |
|---|---|---|
| 照片 | 中 | 能证明「这一刻边界是什么」，不能证明「从未闪过」；**必须写明拍摄条件**（档位、光照、机型） |
| 日志行 | 高（若枕上 `-log1`） | 差刷路径打 `diff bbox` 与 `bg` 值，「这页刷了几次、填的什么色」可复算 |
| 计数 | 中 | 只对「刷了几次」有效，对「有没有色斑」无效 |

**没有载体的一页不许记 ✅**——宁可记「待定」，也不把「没看」写成「没斑」。

**不预设每页同色**：`0xEE` 这种值在首页卡片区已经存在，条带区完全可能有第四种。

## 七、下一轮的第一步：8 页批量读码（命令已验）

> **v3 措辞修正**：本节原来的「本轮不跑全量」与下面的「实跑输出（当前树）」并存，读起来像自相矛盾。
> 准确说法是：**批量普查已跑**（下面那段 for 循环的输出是原文），**逐页深读未跑**
> ——每页三问、底色候选、无斑载体仍是下一轮的事。**跑的是面，不是点。**

**逐页深读下一轮执行**：

```bash
# 哪些页面画状态栏、各自有没有 status_bar_bg 回调（一次扫全）
for f in main/apps/*.c; do
  n=$(grep -c "ui_nav_status(fb)" "$f" 2>/dev/null)
  if [ "$n" -gt 0 ]; then
    echo "== $(basename $f) (${n} 处) 回调=$(grep -c 'status_bar_bg=' $f) =="
  fi
done
```

**三个数，三种口径（不要混着读）**：

| 数 | 口径 | 构成 | 用途 |
|---|---|---|---|
| **9** | grep 文件口径（`ui_nav_status(fb)` 的 `.c` 数） | 8 页停表 + 首页（已开） | 确定扫描范围 |
| **8** | 问题面（盘点口径：状态栏时钟停的页） | 书架 + 其余 7 页 | 问题有多大 |
| **7** | 待点亮（8 − 书架已开） | 文件 / 设置 / 传书 / 图片 / 目录 / AI / 开机恢复 | **开工清单** |

**书架留在对表里作已知参照**（它是唯一有实测档数 + 无斑照片的一行），所以「8」里有它、开工只有 7。
三个数都对，层面不同——**账面必须写明读的是哪个口径**，否则 9/8/7 看起来像三个矛盾
（纪律 21 在本轮的第三次适用）。

**每页三步**（照 §四）：

1. ① 找 `ui_nav_status(fb)` 的每个入口，看它前面是 `ui_clear_page` 还是专门填充；
2. ④ 用 `-E` + 花括号转义确认条带区有无整块填充（注意 `UI_NAV_TOP` 与 `UI_STATUS_STRIP_H` 是不同高度）；
3. ③ 以 `UI_STATUS_STRIP_H` 引用点为准判断「谁画整条」。

填表时四列必须同时有值才算「可开」：**静态底候选（读码）/ 真机档数（实测）/ 无斑（观测）/ 载体（留名）**。
