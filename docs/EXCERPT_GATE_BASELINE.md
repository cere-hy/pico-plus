## 五、S26-3 bit2 黄金向量（tools/excerpt_ai_golden_test.c，3 组）

**规则**：期望字节由**人按布局手推**（spec 侧），固件编码器的输出必须逐字节等于它；
不一致时先怀疑实现。运行：`bash tools/run_excerpt_ai_golden.sh`（ASan/UBSan，`-Werror`）。

| # | 向量 | 手推要点 |
|---|---|---|
| 1 | 单帧短文本 | word="读"(E8 AF BB)、ctx="读书破万卷。"(18B)、payload=25=0x19、flags 落在 out[13]=0x04 |
| 2 | 两帧塞满首帧 | word="ab" → 首帧 ctx 预算 228；payload=234=0xEA，ctx 恰好铺满 [13,241)；帧1 payload=3 |
| 3 | bit0+bit2 组合 | flags=0x05；首帧 flag 偏移 = 10+word_len；后续帧不带 flags |

## 十、候选包的有效性边界（2026-10-31 定档：验收对象是当时的 bin）

**为什么单列一节**：物理六步的结论只对**跑六步当时的那个 `Read_Pico.bin`** 成立，不对
「某个版本号」成立。不写死这一条，11-14 还账那天「包变了六步还算不算」必成扯皮账；写死之后，
争的是事实（sha256 同不同），不是记忆。

**分类（唯一判据 = sha256，不看版本号、不看 changelog 措辞）**

| 变更类型 | 六步结论 | 台账状态 | 附加要求 |
|---|---|---|---|
| bin 不变（文档 / harness / 登记簿 / 结构牙） | 可沿续 | `CARRIED` | 理由 ≥10 字符，且上一行 sha256 相同 |
| bin 变一字节（产品代码 / Kconfig / 编译选项） | **作废重跑** | `PENDING` 或 `VOID` | 不许写 `CARRIED` |

**载体与牙**

- 台账：`docs/ACCEPTANCE_LEDGER.md`（`PENDING` / `PASS` / `CARRIED` / `VOID` 四枚举，理由一律必填）；
- 牙：`tools/check_pkg_validity.py`，已接进 `run_book_management_tests.sh`（紧跟账本牙）：
  ① 最新一行的 sha256 必须等于当前构建产物（`build_*/Read_Pico.bin` 中 mtime 最新那份）；
  ② `CARRIED` 必须真沿续（上一行 sha256 相同 + 理由够长），**bin 变了写 `CARRIED` 即红**；
  ③ 日期 `YYYY-MM-DD` 且不晚于今天；④ 状态只认四个词；⑤ 无产物打印 `SKIP`（**必须可见**，不静默）。
- **验咬六例（五咬 + 一反）**：⑫ bin 变了还写 `CARRIED`（同时报「沿续非法」与「台账 ≠ 产物」）/
  ⑬ `CARRIED` 理由写「ok」/ ⑭ 第一行就 `CARRIED`（没有可沿续的上一次）/ ⑮ 状态写成「沿用」
  （枚举外）/ ⑯ 送验日期写到 2027-01-01 / ⑰ 合法的 `CARRIED`（sha 相同 + 理由充分）**不咬**。

**与门禁的关系**：这条牙不判「六步有没有跑」（那是人的证据），只判「声明与产物是否同一个
东西」——**声明可以撒谎，哈希不行**。它进的是每次全门禁，不是出包清单：绑错对象这件事，
越早发现越便宜。

## 十一、26.9.31a 物理拔卡死锁（S1–S4 / M123–M126，2026-10-31 冻结）

**为什么这一节进基线**：本轮真机把「在看书界面物理拔卡」打成了两件事——屏幕弹回书架（观感
即闪退），以及**插回后彻底不认卡、必须重启**。后者的判据此前一条都没有：`sd_probe_host_test`
只模拟「卡没了 → 掉盘 → 重挂」的事件序列，真机给的是「CD 弹跳 + 首发挂载失败 + 封面任务在读」
的状态交叠。四条用例咬的就是这个交叠，不是任何一个事件。

| 用例 | 造什么 | 断言 | 现场对应 |
|---|---|---|---|
| S1(a) | 3 次采样里第 2 次 absent | `sd_present_stable()` 返回 `ESP_ERR_INVALID_STATE`（**无判决**）；稳定时返回 `ESP_OK` | 344796 ms 那次单点 `present=0` |
| S1(b) | 探测期（`probe_state==1`）一次 absent / 已挂载卡消失 | 前者**不置位** `media_invalidated`；后者必须置位且快照落成「卡不在」 | 91855 ms 那次锁存 |
| S2 | 锁存为真 + `present` 上升沿（无残留句柄） | 闩被清除、`probe_state=0`、`start_probe()` 必须真的建任务 | 插回后不认卡 |
| S3 | 20 轮「CD 抖 + 四档全失败」 | 每一轮 `remount()` 都返回 `NOT_FINISHED`；`start_probe()` 不再吐 `INVALID_STATE` | 382146 ms 那条无限重复 |
| S4 | 锁存期内 `publish_info(mounted=true, error=OK)` | 闩被握手清掉，发布结果**不得**被抹成未挂载 | 环③（挂载成功 vs 宣布无卡） |
| S5（app_loop） | 卡在位、挂载硬失败（`ESP_ERR_TIMEOUT`）×32 步 / 12 s | 重试次数 ≥5——三次快速重试之后**还在重试** | 「只能重启才恢复」 |

**变异（`tools/run_sd_mutations.sh`，4 靶点，必须全 killed）**

| 编号 | 变异 | 咬它的用例 |
|---|---|---|
| M123 | 锁存判据放回 `\|\| probe_state == 1` | S1(b) |
| M124 | 删掉上升沿清锁存 | S2 |
| M125 | `SD_CD_SAMPLES` 退化成 1（单采样） | S1(a) |
| M126 | 看门狗退回「上限 3 次」 | S5（app_loop） |

**修前必红**：M123 与 M125 逐字复刻 26.9.29 的语义，S1/S3 在它们下面各自 Aborted——
这就是「先红后绿」在本轮咬的活物（第三次：前两次是 B31 咬 `on_key`、M115 骗过牙）。

**驱动事实（读码结论，行号可查，不许「读过了」）**

| 事实 | 出处 |
|---|---|
| 单条 SD 命令上限 1,000 ms | `esp_private/sdmmc_common.h:46`（`SDMMC_DEFAULT_CMD_TIMEOUT_MS`）→ `sdmmc_cmd.c:49-52` 取值 |
| 一次 `read_blocks` 失败可能花 2×1,000 ms（失败后还发一条 CMD13 取状态） | `sdmmc_cmd.c:643`（`sdmmc_read_sectors`）→ `:659` → `:713`（`_dma`）→ `:740`（`sdmmc_send_cmd_send_status`） |
| 真机实测单次失败 ≈ 117 ms | 现场 344796 ms（判 `NOT_FOUND`）→ 344913 ms（`returned 0x107`） |
| `sdmmc_host_init()` 幂等 | `esp_driver_sdmmc/legacy/src/sdmmc_host.c:78-83`（`if (s_ctlr) return ESP_OK`） |
| `sdmmc_host_deinit()` **不**幂等，第二次返回 `INVALID_ARG`（不二次释放） | 同上 `:173-189` + `esp_driver_sd_intf/sd_host.c:19-24`、`:65-71` |
| deinit 之后必须重新 init 才能 `init_slot` | `sdmmc_host.c:146`（`add_slot` 直接吃 `s_ctlr`） |

**8 次超时账（P1-1 的答复）**：8 × 2,000 ms = 16 s，**装不进「3 s 内判 lost」**；8 × 117 ms ≈ 0.94 s
才装得进。所以判据只能按墙钟写（`now - t0 ≥ 3 s` 无条件判 lost），重试次数只是快路径，

### 13.3 超集代验（台账规则，替代「回旧包跑一遍」）

- **定义**：新包若是旧包的功能超集，且差异可机器证明（符号差集 / 段对账 / `git diff`），
  则旧包判据可在新包上一次跑完，台账两行同结，不多花一次刷机。
- **绑定**：两行都绑新包 bin 哈希；旧包行备注「由 `<新包>` 超集代验，`<路径>` 零改动
  （`<commit>` diff 为证）」。
- **失效条件**：新包若动了旧包判据涉及的任何路径（哪怕一行），代验作废，必须回旧包跑。
- **31a 的具体适用**：摘抄七条 + 死锁三判据全在 31a bin（`aea69a2f…`）上一次跑完；
  26.9.29 行绑同一哈希并注明「摘抄路径零改动（`390189f` diff：`excerpt_store.*` /
  `check_excerpt.py` / 13 组用例零命中）」。

### 13.5 证据形态三课（2026-10-31 立）

| 骗人的东西 | 形态 | 武器 | 首例 |
|---|---|---|---|
| **段值骗人** | 段总大小 +0，符号却在变（或反之） | nm 差集 + readelf 段读数 | §13.2 起三例，第四例见 §22.6 |
| **哈希骗人** | 同源码重建哈希不符 → 误以为封版被破 | 三角绑定（字节数 + 符号表 + commit） | §22.6 |
| **绿灯骗人** | 门禁全绿，牙的检查对象早已不在原位 | 牙体检（§13.4）+ 先红验证 | B41 死牙（本轮） |
| **快照盲区**（2026-11-01 补） | 状态位每拍都对，**边沿不在快照里**：日志与快照都诚实，事件不可见 | 事件计数器（epoch / 计数），不用差分 | E-2 挂载让行（§13.30） |

**快照盲区机理**：这一类不撒谎，它是**采样**。快照只回答「此刻是什么」，不回答「此前发生过
什么」；「边沿 / 次数 / 时序」这三类属性天然不是快照能承载的对象。两类发作形态见 §13.30
（插拔快于观察周期 / 边沿先于观察者存在），共同点是**每一张快照都对**——所以靠「多看几眼日志」
永远查不出来，只会看到一片正常。

**通用武器一行（入册）**：**凡「边沿 / 次数 / 时序」类属性，用计数器，不用差分。**
差分是两次快照的减法，它的正确性依赖「两次采样之间没有事件」这个假设；计数器不依赖任何采样
假设，只数发生过几次。这条与 §13.4/B51（推断 → 可查询事实）、§13.21/B55-B56（符号存在 →
真的在用）同一条主线：**代理物（推断、快照、符号）都可能对而全，事件计数器才是实物。**

三条共同点：**证据本身会过期**，不复核的证据比没有证据更危险（它会给出假的安全感）。
凡是"绿"，都要能说出它绿在哪儿。

**第 8 例机理（快照盲区）**：粒度 = **采样**。前七例都是「某个证据说错了话」，本例是
「证据每句都对，但它回答的不是那个问题」——快照答「此刻是什么」，问题问「此前发生过什么」。
所以它连「红灯」都不给：没有异常可看，只有一段安静的、功能确实失效的时间。武器 = **事件计数器**
（见 §13.5 表新增行与「通用武器一行」）。这一例的家族意义：**「诚实且完整」不等于「够用」**，
采样对象选错时，采样频率再高也没用——这是 §13.3「测试对象选错」在证据侧的镜像。

**第 6 例机理（绿灯骗人）**：粒度 = 「牙」。门禁全绿不等于牙活着——B41 在抽层后检查对象
已从原位置消失，牙永远绿，检查作用为零。机理：**危险模式整体移到 `push_part` API 边界之后**
——exec 体不再直接碰 FILE\*，而经 API 传递的存储工作旧牙够不着。武器 = **牙体检**（结构重构
逐颗核对检查对象是否仍在原位）+ **先红验证**（新牙/改牙交付前置）。

**第 7 例机理（推断当事实陈述）**：粒度 = 「句子」。审计句「禁名 `fclose` 等在抽层后的
`push_sink.c` 里不可能出现」是从分层逻辑**推**出来的、不是测出来的——实测四个禁名里
**truncate 0 处**（唯一永久消失者）、**rename 4 / remove 5 / fclose 1 处仍在**。

### 13.7 31b 清单第 1 条子项（2026-10-31 立，并入送审稿）

**来源**：B51/B52 证据任务付的租金——三拍 quiesce 的「push 空闲或封送已停」判定，
**只数会话状态机会漏**。

**BLE 接收路径持有的 FILE\***（两类，都在 BLE 任务手里）：

| 句柄 | 位置 | 持有期 |
|---|---|---|
| `.part` **写**句柄 | `push_part.c:115` `fopen(PART_PATH,"ab")` / `:122` `fopen(PART_PATH,"wb")` | 会话接收期间**常开**，直到 `do_commit` 首行 `push_part_close()`（`push_sink.c:1108`）或 discard/rewind 才关 |
| `.part` **读**句柄（`do_verify`） | `push_sink.c:994` `fopen(PUSH_PART_PATH,"rb")` → `:1003` `fclose(r)` | 同步窗口（进出同一函数），.verify 读的是 **`.part`** 不是 push.txt |

**判定缺口**：三拍 quiesce 若只看 `push_sink` 的会话状态机，这两类句柄的持有期都不可见；
卡恰在窗口内被拔 → quiesce 照常通过、卸卷照常执行。与 B52 同根（句柄在第三方任务手里）、
与 26.9.31 根因 C 同形。

**记账方式（31b 送审时写进三拍协议判据）**：

> push 判据 = 会话状态机空闲 **∧** BLE 路径 FILE\* 计数为 0 **∧** **quiesce 进行中会话入口冻结**

第三合取项为什么必要：ARM 时刻的 adopt `truncate` 是**无句柄**存储操作，**句柄计数看不见它**
（§13.2 方向 B）；而掉卡 quiesce 进行中 BLE 照常工作，手机此时推送 → ARM 照样进来 →
truncate 照样碰正在卸载的卷——**covers 同形第三次现身**（句柄窗口 → B52 方向 B → 本条）。
**不新增机制**：入口闸本来就要做（§13.2 闸门收敛版），31b 只要求三拍期间它同样生效。

计数用 push_sink 内部量（`s_part` 指针 + verify 句柄进出加减），**不新增跨组件状态**；
verify 是同步窗口，进出加减即可。

**真机 7a 观测（已入执行计划，只采集不作判据）**：记 `do_verify` 开/关 `.part` 句柄与阅读器
重开 push.txt 的时间戳关系。

### 13.8 任务拓扑是安全属性（2026-11-01 立）

**规则**：任务拓扑**免费提供的互斥**是安全属性的一部分。任何任务迁移（封送、新任务、
回调改线程）落码前必须做**拓扑重审**——枚举旧拓扑的免费互斥清单，逐项指认迁移后由谁接管；
**无人接管的项，要么同批补闸、要么不迁移**。

**在账三案同根**（都是「免费互斥被拿走而没人接」）：

| 案 | 形态 |
|---|---|
| covers | 句柄在第三方任务手里，收口（quiesce）不可见 |
| B51 | verify 对 quiesce 不可见（顺序靠拓扑不靠协议） |
| A′ 反咬 | 迁移拆掉免费互斥，把不可达变成跨任务可达 |

**措辞纪律（本节连带，强制）**：A′ 与 B51 的「不可达 / 不可能重叠」表述**必须带拓扑限定**
（「**在当前拓扑下**」）；不带限定的绝对表述不许出现——拓扑一变结论重审，这正是 A′ 反咬的
全部含义。

**封送 VERIFY 的拓扑重审模板（push 线下一批直接用）**：

| 配对 | 当前拓扑的守护 | 封送 VERIFY 之后 |
|---|---|---|
| verify ↔ 四拍 | 同回调栈同步执行 + 状态机顺序（verify 是 COMMIT 前置门） | 同落主循环，**仍互斥** |
| verify ↔ fresh | 同回调栈（**A′ 的依赖项**） | **跨任务，互斥丢失** |
| 四拍 ↔ fresh | 跨任务（方向 A/B 所在） | 不变——本来就要入口闸 |

**收敛点**：入口闸（挂起到终态）**无论迁不迁移都必须建**（B52）；建好之后恰好也接管封送后
的 verify ↔ fresh——**一个机制盖住三个暴露面**。这不是选型结论（选型仍归下一批），它说明的
是闸门在两种拓扑下都是必需项：**封送 VERIFY 因此不再被 A′ 一票否决，只需同批带闸。**

**push 线下一批前置条件（已钉）**：封送 VERIFY 若做，必带闸同批。

### 13.9 真机验收包络纪律（2026-11-01 立，7b 为第一例）

**规则**：真机验收的动作必须落在**真实使用包络**内。打不到的分支不许靠扭曲使用场景去够，
改由非真机手段（宿主用例、变异、静态牙）覆盖，或如实记「未覆盖」。「罕见 ≠ 已验证」——
罕见只是不阻塞出包的理由，不是免于记账的理由。

**两条判定边界**（防止把「包络」读宽或读窄）：

| 类别 | 判据 | 例 |
|---|---|---|
| **交互动作**（翻页、拔插、按键） | 按**人类节奏**判 | 「连翻 20 次」不够格；正常翻页 2–3 次够格 |
| **状态**（卡满、卡坏、低电、DMA 碎片） | 按**用户可遇性**判 | 卡满是真实状态，人为灌满 = 状态注入，不是扭曲动作 |

**存疑时不自判**：某动作「人到底会不会做」拿不准，写疑问句问需求方（疑问句协议延伸到需求侧）。

**第一例（立规的由来）**：7b 的 busy 分支真机 0 命中（`dropped after` 0 / `ERR(7)` 0，最慢
1474 ms 未越 1500 ms 死线）。执行侧提议「连翻 20 次 / 开词典面板」强行触发，用户否决——
理由「违反正常人类阅读操作」。**建议撤回**，改为宿主跑两拍真身（见 §13.10）。这是本纪律的
第一个正确走法：打不到 → 换通道，而不是加码演员。

**需求卫生规则（同日立，代价直接来自本轮）**：用户口头需求落台账前必须补齐**场景三问**——
**哪个界面 / 什么时机 / 期望什么**。本轮「纯文本列表」四个字要分出三个批次（拔卡后降级提示 /
书架纯文本 UI / 摘抄本呈现形态），就是因为缺这三问；补问一轮即可定向。
**不许拿猜测填位**，那正是第 7 例（推断当事实）的生成机制。

> **结案（2026-11-01）：【纯文本列表】已由需求方正式撤回。**
> 定性：**内部探讨期的备选方案，需求方未作最终决定**，不构成需求。
> 处置：**从全部计划台账划掉**，三问流程即刻停止，书架**保持原样**（本版不动）。
> 三问规则本身保留——它是通则，不因首例撤回而失效；撤回只说明「没立项的东西不该先进台账」，
> 与本轮缺三问的教训同源：**需求进台账的门槛，比需求澄清的门槛更高一档**。

### 13.10 出包门第 4 条门面改写（2026-11-01，拆半批准）

原门面「欠账三态真机验」改写为两段：

| 段 | 判据 | 状态 |
|---|---|---|
| **机制** | 写失败 → rewind → 重试 → 欠账 → drain → 补不上则 CANCEL+ERR。由**宿主注入证据**结案 | 三案逐案有断言 |
| **形态** | FATFS 真卡满 ENOSPC 的分配行为 | **残留风险**进交付说明，带升级触发器 |

**注入三案与断言**（同一注入层：`push_part_test_short_next_write/short_writes`，即真实短写
而非伪造 rc；旧口径「宿主造不出瞬时忙」随 shim 解除）：

| 案 | 用例 | 断言 |
|---|---|---|
| 1 重试成功不重复不缺 | **16h** | 短写一次 → rewind 到本包起点 → 结果长度精确 341（多 1 B = 重复）、前缀不动、偏移对得上 |
| 2 欠账保留整包 | **16g** | 连败两次进槽、返回值仍 true、盘上不含该包；下个包先 drain 补它；END 前显式 drain |
| 3 槽接不住 → CANCEL+ERR | **16i** | drain 返回 false、槽作废（再 drain 不写任何字节）、句柄关闭、半包由下次 adopt 截回 |

**变异刀位**：M122（重试前不回退）/ M123（补不上不关句柄）/ M124（槽不作废），
**10/10 killed，红全部落在指名用例上**。M124 首轮存活，暴露 16i 断言不够硬（短写注入只
生效一次，第二次 drain 会「成功」掩盖槽未作废）——补「一个字节都不许再落盘」后咬死。

**升级触发器**：任何真机或用户侧出现卡满行为异常（丢数据、假成功），**P1 立修，不走常规排期**。

**与 §13.9 的关系**：卡满是**可遇状态**，拆半裁的是测试成本与宿主可近似度，**不是规避包络纪律**。

### 13.12 牙体检第三例：`transfer-ui` 被两次打死，且**三周没人知道**（2026-11-01）

§13.11 记的是「牙变哑」，本例更狠：**牙根本没被编出来**——编译失败，连哑都算不上。

**发现路径**：26.9.30 自编门禁（`run_26930_gates.sh`）第 10 步 `run_book_management_tests.sh`。
此前各批次的门禁**从未跑到这一项**，所以它从红到被看见，中间隔了 commit 3 到出包的两天半。
**门禁没覆盖 ≠ 全绿**——这是「绿灯骗人」家族的新形态：**没跑的项也显示绿**。

**三层红，逐层剥开**（每层都只有把上一层修掉才看得见）：

| 层 | 引入 | 现象 |
|---|---|---|
| A | commit 3（`136845c`） | `app_transfer.c` 新增 `#include "esp_timer.h"`；`tools/transfer_ui_stubs/` 无此桩 → `fatal error: esp_timer.h` |
| B | commit 5 抽层（`2d3173e`） | `transfer_commit.c` 带走了实现，但两个 runner 的 gcc **编译单元清单没加它** → `undefined reference to transfer_commit_pump` |
| C | 补 B 之后 | `undefined reference to app_book_release_hold` —— 该替身原为 `static inline`（同 TU 有效），抽层后调用方在**另一个 TU** |

**修法（只动测试设施，产品代码零改动）**：

1. 新增 `tools/transfer_ui_stubs/esp_timer.h`（单调 +1 ms 桩，专供 transfer-ui；它不判死线）；
2. `transfer_ui_test_env.h` 补三个 push_sink 替身（`take_commit_request` / `run_commit` / `commit_abort`）；
3. `transfer_ui_host_test.c` 补 `app_book_release_hold` 的**真符号**替身（注释写明为何不能是 inline）；
4. `run_book_management_tests.sh` 与 `run_transfer_ui_host_tests.sh` 的编译行补 `main/apps/transfer_commit.c`。

**先红后绿**：A → B → C → `transfer_ui_host_test: PASS`。三次红全部指名，无「红在别处」。

**一条反证（顺手得到，值得单记）**：修 A 时先试了「删掉那个 include」——`app_transfer.c` 里
它**零使用点**（抽层已把 3 个 `esp_timer_get_time()` 搬走），看起来是死 include。删完重建：
字节数 4,132,176 不变，**哈希 `0e66a922b65d` → `1c69516be085` 变了**。恢复该行再重建，
哈希回到 `0e66a922b65d`。结论两条：
①同一 build 目录增量重建**是可复现的**（同源码 → 同哈希），不必再拿「哈希不可复现」当挡箭牌；
②**「无使用点的 include」不是零影响**——它改变预处理后的 TU，进而改变优化与布局。
所以「顺手清理死 include」在出包前是**禁止动作**：它会让交付物与已批准的 bin 对不上。

**通例升级（§13.4 增补第三条）**：抽层/搬家时，**三处清单必须同批核对**，缺一即死牙——

| 清单 | 位置 | 漏了会怎样 |
|---|---|---|
| 产品构建 | `main/CMakeLists.txt` | 真机链接失败（这条最不容易漏） |
| **宿主 runner** | `tools/run_*.sh` 的 gcc 行 | 牙编不出来，**门禁显示绿**（本例） |
| **桩目录符号面** | `tools/*_stubs/` | 补上编译单元后仍缺符号（本例 C 层） |

**顺带探明的第四颗（本轮不修，登记不变）**：修 `transfer-ui` 时按同法试修 `test_sd_media_guard.py`
（KF-7.3，登记形态 `fatal error: esp_timer.h`），补桩后编译通过，随即在运行期挂：

```
test.c:126 snapshot_reader: Assertion
  `info.mounted && info.capacity_bytes==1048576 && info.free_bytes==524288' failed.
```

**第二层根因已探明**：26.9.23 的 S23 把容量查询改成 deferred（`probe_fill_space_deferred`），
探空要跑一个任务；测试桩的 `vTaskDelay` 是空实现，任务永不推进，快照线程读到的 `free_bytes` 是 0。
**这不是新缺陷，是同一颗死牙的第二层**——先编不过（第一层，已登记），编过了则期望脱节（第二层）。

**处置：回退试修的桩，登记形态与到期日（2026-11-14）不动。** 理由三条：
①它属 26.9.23 的欠账，不在 26.9.30 出包门范围内，本轮不动产品代码也不改测试判据；
②真要修是「把空 `vTaskDelay` 改成驱动 pending 任务 + 让 `finish_probe` 容忍空」，
**改的是桩的调度模型**，属重建而非补丁，须单独成批并带 A/B；
③**改测试断言去迁就产品行为**是「为了让门禁绿而改判据」，本项目明令禁止。
第二层结论写在这里，等复活时直接用，不必重新摸一遍。

> 因为「不是本轮的」就不管——它悬空的是所有人的判断。

### 13.12a 补一形态：**进了门禁，但靶子是假的**（2026-11-01，桩头枚举拍平）

§13.12 记的是「没进门禁 → 没人知道它在红」。这一条更阴一档：**测试注册了、跑了、绿了，但它
证明的对象在固件里不存在。**

`tools/app_loop_stubs/read_pico_transfer.h` 把两个 enum 拍平成一个，还把 STA/AP 整体挤后一位：

|---|---|
| `MODE_{AP=0, STA=1}` | `STA=1, AP=2` |
| `STATE_{STOPPED=0, STARTING=1, READY=2, UPLOADING=3, ERROR=4}` | `STOPPED=0, STA=1, AP=2`（扁平） |

**这一族的三档，按危险程度递增**：

| 档 | 形态 | 谁知道 |
|---|---|---|
| ① 没进门禁 | §13.12：编不出来/跑不了，没人跑 | 不知道（但也不误导） |
| ② 进门禁但断言弱 | §13.21a 弱牙三型：符号存在即算过 | 不知道（且绿） |

③ 的判据只有一条能咬：**桩头副本与真实头的同名常量必须相等**（`check_api_surface.py`）。

**边界（审计批注，暂不扩）**：同名不同值已覆盖；真实头**新增**符号而桩头缺失的场景由
**编译失败**兜底（`undefined` 比静默错位更好），不另设判据。

4. 盘点结果落纸后，总入口的清单本身成为牙：**脚本目录里新增文件而未登记 → 红**。

**首次盘点的两条实证（2026-11-01，落码第 2 条时撞出来的）**：

1. **抽取式 harness 是第四处符号面。** §13.4 的三处清单（产品 CMakeLists / runner gcc 行 /

   → 三处清单升为**四处**：产品构建 / runner gcc 行 / 桩目录符号面 / **抽取式 harness 前奏**。

2. **括号扫描不跳注释 ⇒ 注释里的 ASCII 引号会改掉整颗牙的边界。** 本次在 `turn_page()`

   `resize_text()`——后者引用 `s_px`，于是报「s_px undeclared」，**而根因和 s_px 毫无关系**。
   → 纪律：**被抽取式 harness 覆盖的函数体内，注释只用全角引号或 prime（′），不用 ASCII `'` `"`。**
   这类失败的表象永远指向越界吞进来的那个符号，不指向真正的破坏点——与「哈希骗人」「段值骗人」
   同族：**报错位置 ≠ 故障位置**。

3. **盘点的第一批样本已经够了（同批顺手跑出来的，全部用旧代码复验过「本来就红」）**：

   | 脚本 | 状态 | 位置 |

   | `settings_entry_clock_host_test.py` | **红（`ui_fill_rect_fast` 未声明）** | **不在任何 runner 里** |
   | `reader_refresh_release_host_test.py` | 红（`git show 4bd2b9e…` 对象缺失） | 不在入口 |

### 13.17 空体不是无内容（2026-11-01 立，第二例）

**判据**：任何送审材料的第一道检查是**字节数**，不是内容。字节数为 0 即判「未达」，
不进判读环节。

**为什么要立**：26.9.30 冒烟日志送达时是 0 字节（沙箱副本 `empty`、COS 对象
`HTTP 200 / SIZE=0`、签名有效无 403/404）。若按「用户说测过了」记账，就是把推断写进台账——
家族第 7 例。**没收到 ≠ 没发生**，与 §13.12「没跑 ≠ 绿了」是同一枚硬币的两面：
两者的输出形态都是空白，正确处置都是**不记账**。

**必须区分两件事**：

| 形态 | 含义 | 处置 |
|---|---|---|
| **空体**（0 字节 / 解出为空） | 通道或生成端故障 | 要求重发，不判读 |
| **无内容**（有字节但无目标行） | 结论：目标行为未发生 | 可判 FAIL |

把前者读成后者，会得出一个**方向完全相反**的结论（「设备没输出」vs「日志没进来」）。

**这是第二例**：第一例是 31b 送审 zip 在审计侧解出为空（改成单文件纯文本后解决）。
两次共性不是某个人粗心，而是**附件通道没有空体校验**。统一处置：

1. 送审优先纯文本直贴或单文件，避免多层容器；
2. 送件时**自报字节数**（几十 KB 的日志自报一次，判读端一眼可比）；
3. 判读端先 `wc -c` 再看内容，空体当场退回，不进入判读；
4. 附件重传时给一条**量级判据**帮送件人自查。**但量级只能参考，不能当门槛**——
   初版写的「3–30 KB」是错的（第 7 例第 5 发，执行侧自查抓获），8 份真机日志实测 **58–242 KB**；
   而 2026-11-01 11:58 那份**有内容且判 PASS** 的日志只有 **22.8 KB**，因为它是一次 87.5 s 的短会话。

   **正确的完整性判据是首尾标记 + 时间跨度，不是字节数**：

   | 判据 | 合法形态 |
   |---|---|
   | 首行 | `---- Opened the serial port COMx ----` |
   | 末行 | `---- Closed the serial port COMx ----` |
   | 时间跨度 | 与自报的会话时长一致（本例 87.5 s） |
   | 编码 | UTF-8/CRLF，无 NUL、无二进制 |

   拿 KB 数当门槛的后果是双向的：短会话被误判「日志不全」要求重发（22.8 KB 这次差点如此），
   而真正被截断的长日志反而因为「落在区间内」看不出来。**字节数只用来判空体，不用来判完整。**

### 13.19 bss 增量不等于数据量（2026-11-01 立）

31b 第 1 条的静态量只有 6 B（`uint8 flags` + `uint32 ms` + `uint8 depth`），`.dram0.bss`
却涨了 **32 B**。先怀疑自己：三个布尔并成一个标志字节、深度改 `uint8_t`、时长复用
`s_frozen_ms`——**压缩前后段增量都是 32 B**，说明瓶颈不在数据量，在链接对齐。

**结论**：段账要按**段表实测**记，不能按「我加了几个字节」推。反过来说，用「压缩变量」去
救 bss 预算，效果可能为零——**先测再压**，别把本该送裁的事做成无效优化。

**记账纪律**（与 §13.5 三课同族）：内存账写两行——**变量字节数**与**段增量**，两者不等时
必须写明差额归因（本例：26 B 对齐）。只写一个数，下一个读者会以为另一个是错的。

### 13.20 预算单位从字节改为**段量子**（2026-11-01 立，随 A 案批准）

31b 第 1 条把 bss 推到 `0x21580`（31b 累计 +48，超原预算 16 B）。压缩实验已证明杠杆不在数据：
压缩前后段增量都是 32 B，静态量只有 6 B（§13.19）。**A 案批准 +48**，B 案（继续压 packed struct）
否决为默认路径。三条理由，都记在案：

1. **B 是为 ≤16 B 的不确定收益付可读性代价**，还要和链接器搏斗——§13.19 的教训就是段增量不归数据管；
2. **预算的本旨是逼出显式记账，不是绝对数**。本轮走到「压缩一轮 → 停 → 申报 → 送裁」，纪律按设计
   工作了一次；**批准是记账规则生效，不是破例**；
3. +48 B 对 136 KB 量级的 bss 是噪声。要防的是**无声爬坡**，本轮是有声的。

**改制（随批生效）**：

| 项 | 旧 | 新 |
|---|---|---|
| 预算单位 | 字节 | **段量子**（链接对齐后的实测段值） |
| 申报触发 | 每增 1 B 都要报 | 落在当前对齐步进的 **slack 内 → 零申报**；跨步进 → **按整档申报一次** |
| 重复停工 | 每条目各停一次 | 同一档只停一次，一句话记档 |
| 批次硬顶 | 0x21600（新设） | 到顶回议，不许就地抬 |
| 收官对账 | 无 | 31b 结束做**一次性三行**：数据量 / 段值 / 对齐差额 |

**本批预算**：E-1 的 4 B、E-2 的 4 B、P1-1 都落在当前步进 slack 内，**零申报**。

**为什么改**：原单位把「变量字节数」和「段增量」混为一谈，于是每一次对齐抖动都变成一次停工送裁——
真正的风险（无声爬坡）没被防住，反而被「必须报数」的仪式感掩盖。段量子制只对**可观测的段值**记账。

| ④ | **黑匣子事件码三元自检**：新增码必须在「枚举 / `note_name()` / `note_is_critical()` 判定」三处同时到位 | 本轮自捕获，见下 |

**④ 是怎么来的（必须记）**：31b 第 1 条给 `PICO_BOOTBB_NOTE_PUSH_FREEZE = 9` 加了码、接了调用，
**却没进 `note_name()`**——黑匣子重放时它会打成 `?`，等于「留痕了但读不出来」，与「失败而不留痕」
同族。这是执行侧自查抓到的，属正向闭环（第 7 例第 5 发之后第二次）。

③ 与 ④ 是同一条纪律的两个面：**新增一个东西时，"还有哪几处必须一起改"必须由脚本回答，不能靠记性。**
四次失效已经足够证明记忆项不可靠。

#### 13.21a 弱牙三型（加严三型，入册）

任何新牙自检按三型过一遍，缺一型不算牙：

| 型 | 形态 | 本轮实例 |
|---|---|---|
| **谓词防短路** | 只查符号存在 → 被 `false &&` / `if (0)` 短路而全绿 | B56 看门狗谓词必须真在判 |
| **`count >= 2` 防单岔** | 多处接线只接一条，剩下静默 | B57 三条失败路径计数 ≥ 3 |
| **拒死代码形态** | 接线被 `if (0)` 包住，日志与符号全在 | B57 `if (0) { s_next_try_ms = ... }` |

**边界（本轮实测）**：`count >= 2` 防得住「只接一条」，**防不住「两条接到同一个码上」**——
两个调用点传同一个枚举时总数仍是 2，而语义已经塌了。修法：按**每个值的分别出现**断言，不按总数。
这条边界写进三型，作为第四型的候选。

### 13.23 冻结态的回码语义（2026-11-01 立，第 1 条核销补账）

**规则**：冻结／忙态的协议回码必须映射「**可重试**」语义（BUSY）。`NOT_ARMED` 类**终态**语义
禁止在忙态使用——终态会让对端放弃重试，把「等一下就好」变成「永远不行」。

**由来**：31b 第 1 条三处入口判点全部回 BUSY，审计核销时把这条从「实现细节」升格为**协议规则**。
它预答了 B52 选型的一半：**冻结期拒收 = BUSY 可重试失败**。ARM 闸的「挂起 vs 拒收」选型仍归 B52。

**另一半（本批补）**：**失败而不留痕**同族——三拍全败进 hold 时原来只有一行 `ESP_LOGW`，
串口日志一丢，下次开机查「push 为什么死了」完全无据。已补黑匣子事件
`PICO_BOOTBB_NOTE_PUSH_HOLD`（`a` = 原因码，`b` = 当时仍开的 FILE\* 数），由 B56 咬住。

### 13.26 `nm` 的类型字母不是段判据（2026-11-01，随 const 表核对项入册）

E-1 交审时记「data +6 B（`k_backoff_ms[3]`）」，依据是 `nm` 首列字母 **`d`**。审计端
一句核对项问到了根上：`static const` 应落 rodata。实测：

| 判据 | 结论 |
|---|---|
| `nm` 字母 `d` | **只表示段没有 R 标志**；Xtensa 的 `.flash.rodata` flags 就是 `WA` |
| `readelf -SW` 段号 15 | `.flash.rodata`，VMA `0x3c1e7d34`（flash DROM 窗口） |
| map | `.rodata.k_backoff_ms 0x3c1e7d34 0x6` + `*fill* 0x2` |
| 段表 | `.dram0.data` **Δ 0**，`.flash.rodata` **+80** |

所以 const 表从来不在 RAM，「补 const 省 6 B」不成立。**判段归属要看段名 + 地址窗口
（0x3c00_0000–0x3c40_0000 = flash DROM），不看符号字母。** 这与 §13.19「bss 增量 ≠ 数据量」
是一对：一个说段增量不归数据管，一个说符号字母不归段管。

**并且**：E-1 的 RAM 账因此更干净——bss +8 B（7 个字段里 4 个新增 + 1 个原位改名），
段值 Δ0，全部落进段尾 padding。段量子制首个零申报实例成立，且比初稿报的更窄。

### 13.28 台账状态列是**牙的输入字段**，不是展示字段（2026-11-01）

本批把 26.9.30 从 `PENDING` 改判 `PASS` 时顺手加了粗体：`| **PASS** |`。人眼看完全正确，
体检批第 0 步也全绿——然后第 11 步 B39 报：

```
FAIL 26.9.30: state '**PASS**' is not one of ['CARRIED', 'PASS', 'PENDING', 'VOID']
```

去掉粗体即过。**这条要记的不是「忘了去粗体」，而是「哪些字段属于接口」**：

| 字段 | 性质 | 允许装饰吗 |
|---|---|---|
| 台账状态列（`PASS`/`VOID`/`PENDING`/`CARRIED`） | **牙的输入** | 否 |
| 台账哈希列、体积列 | 牙的输入 | 否 |
| 登记簿 `out-ok`/`out-gap` | 牙的输入（§13.24） | 否 |
| 事件码级别 `critical`/`normal` | 牙的输入（§13.24 ④） | 否 |
| 正文、说明列 | 人读 | 是 |

**为什么值得单列一条**：这类缺陷有个共同形态——**人眼全对，机器全错**。而它偏偏不会在
「先红验证」里暴露（先红验的是牙的判据，不是牙的输入格式），只有跑一次真门禁才现形。
所以「跑真门禁」这一步不能省，尤其是在只改文档的时候——**改文档也会把门禁改红**。

### 13.30 E-2 落码：让行的锚点从**状态差分**换成**事件**（2026-11-01）

**现场（26.9.31）**：`Mounted` 100.977 → 队列 **100.994 就写卡**（17 ms）→ `mounted=1` 101.863
才开始计 5 s 让行。中间 **886 ms** 里每一次家务片都在无让行状态下冲账。

**根因不是「接在哪个 if 上」**：`gained = !*mounted && ready` 是**状态差分**。拔插快于一次
轮询时，app 侧看到的 `*mounted` 全程为 true——「一直在」与「刚挂载」在快照上**同形**，
边沿一次都不成立。这类缺陷的可怕处是日志上毫无异常：状态位每一拍都是对的。

**诊断升级：状态差分有两类盲区，机理不同，一起闭合**（2026-11-01 审计侧补入）。上一版只写了
第一类，第二类是复核时才看清的——**旧断言的「开机不打扰」正是第二类的副产物被写成了行为**：

| 类 | 盲区 | 现场形态 | 为什么快照看不出来 |
|---|---|---|---|
| **一** | **插拔间隔小于观察周期** | 拔了又插，两次快照都读到 `mounted=1` | 「一直在」与「刚挂载」在快照上**同形**，没有第三个字段能区分 |
| **二** | **边沿先于观察者存在** | 开机就带卡，挂载发生在 `app_loop` 首拍之前 | 观察者的**第一张快照已是 `mounted=1`**，初始边沿在观察开始前就发生了 |

两类都不是「快照写错了」：每张快照都诚实、每个状态位都对，**丢的是快照之间的那段**。第一类的
变量是**采样频率**，第二类的变量是**观察者启动时刻**——所以调快轮询治不了第二类（首拍之前没有
拍），补一个「首次运行当作挂载」的特例也只治开机一次、治不了第一类。**只有事件计数器同时对
两类免疫**：它不采样、不比前后，只数「发生过几次」。这也是为什么对象选 epoch 而不是再补一个
布尔标志——epoch 是 S26-4 的原始意图（「这是第几次挂载」），布尔标志是它的退化投影。

**三处落点**：

| 层 | 改动 | 为什么在这里 |
|---|---|---|
| 组件 `read_pico_sd` | `s_mount_epoch`，**只在 `mount_card()` 成功处 +1**；`read_pico_sd_mount_epoch()` 只读 | 放在 `publish_info()` 会错：空间回填**再发布一次**，一张卡算两次挂载，窗口推到 20 s 后 |
| `poll_media` | 每拍调 `excerpt_store_mount_yield(epoch, now)` | 挂载发现的最早可知时刻 |
| `excerpt_footer_tick` **首行** | 同上，紧邻 `excerpt_store_tick` | 挂载在 `sd_probe` 任务里，poll 最早下一拍才知道；贴着写卡才把窗口压到 **0** |

第三处是比 §19.4a「同一循环片」**更强**的保证：同一函数、相邻两行，中间无物可插。§19.4a 要求
「注明同步点落在哪一拍」——本批的答案是「落在写卡前一行」，不是「下一片再说」。

**幂等在被调方，不在调用点**：两处都调，同一代号只开一次窗。这条把 S26-4 的「只看边沿」纪律
从**调用频率**下移到**状态机**——调用点每拍都调（这是必需的），窗口只开一次（这是不变量）。

**行为变化（有意）**：**开机就带卡现在也让行 5 s**。旧行为「没有获得边沿所以不打扰」是状态
差分的副产物，不是 S26-4 的意图；S26-4 要躲的是**书架扫描**，而开机那一段恰恰扫得最密。
队列此时为空，代价为零。宿主用例与注释都按新语义改写，不留「旧行为更正确」的错觉。

**账**：bss `0x21580` → `0x21580`（**Δ 0**），数据 +8 B（`s_mount_epoch` 4 + `s_mount_epoch_seen` 4）
全部落进段尾 padding；`nm` 实测 `0x3fca5c24` 与 `0x3fcb4720` 各 4 B。段量子制**第二个零申报实例**。

**核销（2026-11-01，审计侧通过）**：三处落点照批；**行为变化批准**——开机带卡让行 5 s，理由三条
（队列冷启恒空、代价为零；开机恰是书架扫描最密段，正是 S26-4 要躲的窗口；正面判据因此**覆盖
开机挂载**，语义自洽无特例）。**epoch 只在 `mount_card()` 成功处 +1**（避开空间回填重复发布把
窗口推到 20 s）与**幂等放被调方**（双调用点同代号只开一次窗）两个防重复设计均确认为对。
账目对账：text +76、bin `2433a4e88edd`（4,136,016 = 4,135,936 + 80 ✓）、硬顶 `0x21600` 余
1,152 B 未动。**「开机不打扰」从行为清单里删除**——它是第二类盲区的副产物，不是设计要求；
若后续有人以「旧行为更省事」为由要求恢复，先读本节两张盲区表。

### 13.31 体检批必须是**串联短路**，不是并行通报（2026-11-01 语义钉子）

门禁脚本原来写 `bash tools/run_gate_health.sh || rc=1` ——体检红了继续跑完，最后 `GATE_RC=1`。
看起来没错，但输出里**两个 RC 并列**：`GATE_HEALTH_RC=1` 和 `GATE_RC=1`。读的人很容易只盯后一个，
或者反过来认为「门禁绿、体检是另一回事」。

**钉死**：`GATE_HEALTH_RC ≠ 0 → GATE_RC 视为无效，不出具`。落地形态是**就地停**：

```bash
if ! bash tools/run_gate_health.sh; then
    echo "GATE_RC=INVALID (health chain is red - not issued...)"
    exit 1
fi
```

**先红验证**（不是「读一遍代码觉得对」）：往登记簿塞一个不存在的文件 → `GATE_HEALTH_RC=1`、
输出 `GATE_RC=INVALID`、后续 11 步**一个都没跑**（日志里 `##########` 只有 5 个，全是体检批自己的）。

**计数澄清（防下次读档算不平）**：五条 `##########` 不是五个门禁步，是 `1 + 4`——

| 条 | 是什么 | 归属 |
|---|---|---|
| 第 1 条 | `0/12 门禁体检批` | **门禁第 0 步的标题**（第 0 步整体算一个门禁步，它内部再展开） |
| 第 2–5 条 | `H1/4` … `H4/4` | **体检自身的四个子步**（H1 盘点 / H2 注册 / H3 接口副本 / H4 事件码） |

所以「12 步、0 步即停」说的是**门禁步一级**：12 个门禁步只产生了第 0 步一条标题，1–11 一条都没有。
全绿时是 **16 条** = 12 个门禁步标题 + 4 个 H 子步。**读档先看编号**（`x/12` 是门禁步，`Hx/4`
是第 0 步内部），不要拿 `##########` 的总条数直接当步数。

这条与 §13.28 是一对：一处说**门禁的输入字段不许装饰**，一处说**门禁自己的结论不许并列**。

### 13.32 `run_dict_hit` 定性：**stale**，不是 bug——但它守的那条链此前无人看守（2026-11-01）

**判定：stale。四条证据**：

| # | 证据 |
|---|---|
| 1 | `26.9.12` 起绘制侧统一到 `line_ink_width()`（同源得到「反色底与字形 run 共用一个右边界」，修的是「右边少盖半个字」） |

把 `line_ink_width()` 内部改成手算 `available`，两个循环体看起来一个字都没变，右边界已经开始

| 处 | 抽象层 | 断言原对象 | 断法 | 守卫 |
|---|---|---|---|---|
| commit 3 批 | `push_part` API | `push_sink.c` 里的 `rename`/`fclose` 字面量 | exec 体不再直接碰 `FILE*`，旧牙够不着 → **死牙**（§13.4 B41） | 转发链断言：API 内必须仍做那三件事 |
| 本节 | `line_ink_width()` | 绘制侧「必须直调 `justify_target_px`」 | 抽层后直调消失，断言失效 → **误判为 stale 的红** | `INDIRECT`：体内必须仍委托 |

否则**抽一次层，断一次盲**。三种处置里只有第二种是对的：删断言（绿，但链断无人知）❌、

### 13.33 31b P1-1 落码：掉盘的**第二个信源**（2026-11-01）

**问题**：「卡没了」此前只有一条信源——CD 脚（`read_pico_sd_detect()`），**无去抖、单次采样**。
CD 擅长「快」（卡一离开槽位就知道），答不了「准」（卡还在槽里、但已经读不出来：触点氧化、
半拔出、卡内部坏）。26.9.31 现场 present 在 888/892/923/927 行之间来回跳，就是单一信源在抖。

**为什么第二信源只能主动读**（这不是设计偏好，是结构约束）：本工程所有读卡都走 FatFs/VFS，
没有自建 diskio 层可挂钩（`diskio_sdmmc` 是 IDF vendor 件），而判据要求的场景恰恰是
「**没人读卡的时候拔卡**」——首页静止、CD 被飞线短接到 present。没有心跳，这个场景永远
等不到第一个 0x107。于是：`read_pico_sd_watch_io()` 每拍被调，内部自带节流
（正常 1 s 一次 512 B、失败态 100 ms 一次），`poll_media` 在 `get_info()` **之前**调用它，
同拍就能落到 lost。

**判据：两处参数不同源**（这是本节最容易被后人改错的地方）：

| 量 | 值 | 角色 |
|---|---|---|
| `SD_IO_FAIL_LIMIT` | 8 次 | **快路径**：卡响应正常时提前收工（8 × 117 ms ≈ 0.94 s） |
| `SD_IO_DEAD_MS` | 3,000 ms | **判据**：`now - t0 >= 3 s` 无条件成立，不依赖次数 |

为什么必须两个：单次 `read_blocks` 最坏 2×1,000 ms（失败后还要发 CMD13 取状态），8 次 = 16 s，
**装不进「3 s 内判 lost」**；实测 117 ms 时才装得进。把它们写成一个数，下一次调采样率就会
互相打架——§13.5 第一课（段值骗人）同族：**一个数字承担两个语义，读的人无法判断该改哪一个**。

**为什么不在失败时忙等 8 次**：app_loop 的 tick 是 5 ms，忙等最多堵 3 s，UI 会肉眼可见地卡。
跨拍累计是唯一不伤主循环的形态——代价是「8 次」的实际耗时取决于采样节拍，所以它只能当快路径。

**只数 0x107**（`ESP_ERR_TIMEOUT`）：其它错误码（`INVALID_STATE` / `NO_MEM` / 参数错）说明
「这次没读成」，不说明「卡不答」。一并计入的话，一次内存紧张就能把好卡判死、卷被无谓卸载——
「准」是这条信源存在的全部理由，宁可漏判一次，不可误判一次。

**判死动作**：置 `media_invalidated`、`cached_info.mounted = false`、`error = NOT_FOUND`，
**不改 `present`**。CD 说在，那是它的事实；I/O 说卷不可用，那是另一个事实。两个都留在快照里，
拼起来才是完整现场——把 present 改成 false 等于替 CD 撒谎，下一个读日志的人会以为槽位开关坏了。

**换卡必须清零**（宿主测试当场抓到）：判死时 `s_io_fails` 停在 8，若 `mount_card()` 成功处不清，
换卡后第一次心跳就带着上一张卡的账立刻判死。修法是在 `++s_mount_epoch` 同一个临界区里清三件
（`s_io_fails` / `s_io_fail_ms` / `s_io_next_ms`）——**新一次挂载 = 新一笔账**，与 E-2 的代号同一处。

**事件码**：新增 `PICO_BOOTBB_NOTE_SD_IO_DEAD = 11`（critical；`a` = 连续失败次数，`b` = 从

### 13.34 B42 上线即绿：牙抓到的是一行**真的假收口**（2026-11-01）

**判据**：`main/` + `components/`（vendor 除外）里 `*_quiesce(0)` 零命中。上线即**红**——
`app_loop.c` 的插拔边沿有一行：

```c
if (gained || lost) { ui_avatar_invalidate(); (void)book_cover_jobs_quiesce(0); ... }
```

`quiesce` 的语义是「收口」：停生产者、收句柄，超时是失败。传 0 = **宣布收口、一个 tick 都不等**，
返回值又被 `(void)` 扔掉。代码写着「我等了」，实际一次没等。卡已经拔了，这行真正想要的是
「别再给我上一页的封面」——那是**作废**，不是收口。

**修法**：新增 `book_cover_jobs_discard()`（= `cancel(s_generation)`，明确的「不等」语义），
边沿改调它；真正的收口留在 lost 分支的三拍里（`push_sink_quiesce(2000)`）。**行为零变化**
（原写法本来就是 cancel + 检查一次），改的是语义与名字的统一。

**牙的三条判据，互相为锚**：

| # | 判据 | 防什么 |
|---|---|---|
| B42a | 代码（**去注释**）里 `*_quiesce(0)` 零命中 | 假收口回潮 |
| B42b | `book_cover_jobs_quiesce(` 的非零调用 ≥ 2 仍在 | 「把 API 全删了」也绿——那是牙被拆了 |
| B42c | `poll_media()` 的边沿必须调 `discard()` | 修法被抹掉（旧封面活到下一本书） |

**去注释匹配的决定**：注释里写 `quiesce(0)` 是在**解释这条牙**，不是调用。这与 §13.27 第三坑
不矛盾——盘点工具靠文本认「资产被引用」（注释里的路径仍代表引用意愿），这条牙认的是
**调用形状**。两者都遵守同一条：**判据不因误报而放宽，放宽的是「什么算调用」的定义，并写清**。

**先红两向**：塞回 `quiesce(0)` → B42a 红；把 `discard()` 换成 `cancel(0)` → B42c 红。

### 13.35 先红工具的回滚锚点是「注入前」，不是 HEAD（2026-11-01，本轮真丢两次码）

`run_tier1_first_red.sh` 用 `git checkout -- <file>` 还原注入。Tier 1 那批没出事，只因为

### 13.37 `s_release_pending` 三收口：一个**顺序**问题被三个条件逼了出来（2026-11-01）

**批复**：合流干跑核销通过；「补卸载闩锁最多 3 次」条款由 31a 环④证据**明文废止**
（计划原文保留，加注废止日期）；照准附三个收口条件，真机刷机前落地。≤3 的废止理由：
它立项时「放弃卸载」看似安全，31a 现场证明放弃卸载本身就是环④（`card` 永非空 → stale card
→ 插回不认卡）。两条计划不是冲突，是**先后**——≤3 写在 31a 证据之前。

#### 一、三个条件的落点（行号即自证）

| # | 条件 | 落点 | 判据 |
|---|---|---|---|
| ① | 重试拍可见 | `app_loop.c:839`（fast `(n/3)`）/ `:852`（慢档 `(try n, frozen)`）/ `:895`（卸载失败 `(err, try n), retry in 10 s`） | 10 s 一拍**逐拍一行**；原 `%6`（60 s 一句）废止 |
| ② | 终态清账 | `app_loop.c:795-797`（`gained` 边沿清 `s_release_pending` + `thaw`，`thaw` 内部清 `FRZ_HOLD`）；卸载成功 `:860` 原有 | 两边都清，缺一边就是「解冻了下一拍又去卸」 |
| ③ | 边界留痕 | 第三方 `FILE*` 永不关 → **冻结 + 重试直到句柄关闭或重启**，写进交付说明，与 B52 入口闸同一账 | 安全降级、非死锁：可观察（逐拍日志）、有出口（句柄关或重启） |

`thaw` 会清 `FRZ_HOLD` 这一点是读 `push_sink.c:2433` 确认的，不是从名字推的：
`s_freeze_flags = 0` 连毒卷标记一起清——所以条件②的「HOLD 归零」由 `thaw` 承担，
`app_loop` 只需清 `pending` 这一半。

#### 二、条件②逼出的真问题：**闩锁块的位置**

31b 的闩锁块在函数最前面，`pending` 为真就 `return false`；而 `gained` 判定在它后面。
于是闩锁一挂上，`gained` **永远走不到**——用户插回的卡明明挂载成功了，闩锁每拍去卸它，
掉卡 → 重挂 → 再卸，循环。条件②要求「挂载边沿解冻时清 pending」，但那个边沿根本进不去。

**处置：整块下移到 `gained` 处理之后（`app_loop.c:803`）**。边沿先行、重试在后：

```
判定 ready/lost/gained → gained（清 pending + thaw）→ 闩锁重试（return false）
```

与 §13.36 主裁决（发布顺序）同一族：**顺序不是实现细节，是语义本身**。本案的顺序错误
不是推演出来的——写用例第一跑就暴露（`lost==0`，见第四节坑 2）。

#### 三、牙：`remounts_before_quiesce` 采样，不是事后问

新场景（`app_loop` 60 场景之一）：push 的 `FILE*` 永不关 → 跑 16 拍；第 15 拍「关掉」它。
断言：等不到时 `remounts==0 && hold_calls==1 && thaw_calls==0 && quiesce_calls>=5`；
恢复后 `remounts==1 && thaw_calls>=1 && remounts_before_quiesce==remounts-1`。

最后一条是牙尖：**旧写法放弃闩锁后只能走看门狗，而看门狗路径不过 `quiesce` 闸**。
顺序采样（`quiesce` 被调时记下当时的 `remounts`）能分辨「绕过闸」与「过闸」；事后问
`quiesce_calls` 分不出。同 §13.31「顺序证据只能采样」与 commit 4 的 abort 采样。

#### 四、三处坑（都靠实测纠正，零入档污染）

| # | 坑 | 形态 | 纠正 |
|---|---|---|---|
| 1 | `if (++x == N)` 改写后判据用了**自增后**的值 | 跨档 `hold` 永不触发（实测 `hold_calls==0`） | 先取 `first_slow = (tries == N)`，再自增 |
| 2 | 用例边界没排空函数 static | 上一场景的 `pending`/`mounted` 遗留，新场景首拍直接进闩锁分支，`lost` 永不发生（实测 `lost==0`） | 场景开头跑一拍「排空」（quiesce 成功 → remount → pending 清零），再重新开账 |
| 3 | `uint8_t` 计数无限自增 | 255 次后回绕，10 s 慢档悄悄退回 1 s fast 档（节拍与日志一起失真） | 饱和在 255：`if (x < 0xFF) ++x` |

第 1、3 条是同一个教训的两面：**「永不放弃」把只跑 3 次的循环变成无限循环，所有依赖
计数的判据都要重新过一遍溢出与自增顺序**。31a 在 `s_retries` 上踩过 `% 6` 的节拍陷阱，
这次轮到 `s_release_tries`。第 2 条属测试卫生：**闩锁/缓存类函数 static 不归 `reset()` 管，
用例边界必须显式排空**——否则上一场景的状态会伪装成本场景的第一个断言失败。

#### 五、TIMEOUT 改动结案（§13.36 修正一的尾巴）

错误推断曾把判死码改成 `TIMEOUT`；实测证明判死码**不决定看门狗入口**（真因在桩）。
处置按批复分两落点，**都已完成**：

| 落点 | 现值 | 理由 |
|---|---|---|
| 产品码 `observe_io_dead()` | `ESP_ERR_NOT_FOUND`（`read_pico_sd.c:734`） | 26.9.31 立项现场实证的判死签名 `err=NOT_FOUND present=0`（344796 行）。改签名会破坏跨版本判读连续性——以后对不上历史签名，判读第一件事得先查「哪个版本改的」 |

#### 二、缺陷：插卡被踢回书架（三个真机样本同形）

```
sd: err=ESP_OK present=1 mounted=1          ← 挂载成功
book: chapter load failed: ESP_ERR_INVALID_ARG
book: shelf books=18 roots=2                ← 回书架重扫
```

t=139446 / 300679 / 473148，**一次插卡一次命中，100% 复现**。第三次发生在 A 摘抄组内，被「冲账成功」盖住了——**功能成功不等于状态正确**，这是本轮最值得记的一行。

**根因（不是 UI 重绘）**：`book_enter_offline()` 为不留悬空 `FILE*` 调 `book_close()`
（同时 `s_book.count` 清零）；`book_leave_offline()` 未重开书源就 `load_chapter()`，
`book_chapter_load()` 的 `!s_book.file` 分支返回 `ESP_ERR_INVALID_ARG`，失败路径把 view 打回 SHELF。
**失败路径本身是对的，错的是它不该失败。**

**修法**：先 `book_open(s_path)` 再 `load_chapter()`；重开后 `s_off_chapters`/`s_off_total_bytes`
对不上（换卡/改内容）→ 锚点作废回章首；`s_chapter` 越界 clamp。

**与 §13.37 同族第二次**：上一次是「边沿必须排在重试前」，这次是「重开必须排在加载前」。
**顺序错误在这一层的复发率已经可以当规律用**——凡是「状态转换 + 恢复动作」写在一个函数里，
先问「哪一步是前置条件」。

#### 三、牙分两层，理由各不相同

| 层 | 位置 | 咬什么 | 为什么非它不可 |
|---|---|---|---|
| 行为 | `book_source_host_test.c` +4 条 | `book_close()` 后 load **必** INVALID_ARG；重开同章可加载；字节偏移语义不变；换内容后 count/bytes 必变 | 钉住「不重开就是这个错」，把真机签名变成可复现断言 |
| 结构 | `check_offline_reopen.py`（11/15） | `book_enter_offline` 含 `book_close`；`book_leave_offline` 含 `book_open` **且在 `load_chapter` 之前** | **删掉那一句，所有宿主测试仍全绿**——app 层无完整 harness（切片 harness 已 KF-7.1） |

结构牙正反两向实测：删掉 `book_open` 即红。**静态牙的正当性来自「行为牙够不着」**，不是来自「静态更好写」。

## 十七、DMA 子池观测上线（26.9.30 线，2026-10-31）

**动机**：26.9.31 真机 `allocate_dma_buf: not enough mem (0x101)` 34 次（启动书架段 25 次
18.05–20.51 s、第 3 轮插回后 9 次 166.20 s），而 bootbb 一直只采 `MALLOC_CAP_INTERNAL`。
driver 要的是 `MALLOC_CAP_DMA`（`sdmmc_cmd.c:26-45` 折半重试，折到 512 B 仍失败才报 0x101）——
「总堆还剩 11 KB」这句话对 DMA 子池什么都不说明。观测缺口是系统第五个「盲区驱动」的点。

**两处实现**（32 行，全部在 `pico_heapdiag`，零分配路径改动）

| 出口 | 覆盖 | 形态 |
|---|---|---|
| `bb_sample()` 内维护 DMA 最大空闲块最低点 → spill 打 `dma floor: largest=%u B at t=%u00 ms` | 启动段（20 s 采样窗内，正好是 25 次那一段） | 段账，`s_min_dma` / `s_min_dma_ms` |
| `bb_dma_note_from()` 在 `SD_STAGE`/`SD_DONE` 事件点派生 `PICO_BOOTBB_NOTE_SD_DMA` | 20 s 窗外（166.20 s 那 9 次） | 事件账，**只在创新低 ≥1 KB 时记** |

派生事件编码：`a` = `largest/256`（饱和 255，步进 256 B），`b` = `原事件码 << 8 | 原 a`。
打印形如 `sd-dma dma_largest=8192 B (sd-stage a=3)`——数值是池底，括号里是「谁把这件事捅出来的」。

**为什么阈值是 1 KB 而不是「每事件一条」**：健康会话里 SD 事件约 20 条/天，每事件一条会把
64 条环在一天内写满，等于把观测变成污染。1 KB 是「不是抖一下」的量级，与 `bb_sample` 的
512 B 变化判据同族但更宽（池底曲线是慢变量）。

**B44 / B45（`tools/check_bootbb_ready.py`，已上线即绿）**

| 编号 | 判据 | 咬什么 |
|---|---|---|
| B44 | `bb_sample()` 函数体内必须出现 `MALLOC_CAP_DMA`；`dma floor` 必须被打印 | 只采不打 = 26.9.18「采到了没出口」重演 |
| B45 | `bb_dma_note_from()` 必须含 1 KB 阈值；`PICO_BOOTBB_NOTE_SD_DMA` 在 `pico_bootbb.c` **之外零命中** | 无阈值会写满环；外部直写会让「派生」变「谁都能塞」 |

**三刀全 killed**

| 编号 | 变异 | 结果 |
|---|---|---|
| M127 | **复刻型**：DMA 采样退回 `MALLOC_CAP_INTERNAL`（26.9.29 的历史语义） | B44 红 |
| M128 | 阈值 `1024` → `0` | B45 红 |
| M129 | 外部直接写 `sd-dma`（`app_loop_run` 首行） | B45 红 |

> M129 第一次**没打中**：变异脚本按 `void app_loop_run(void) {` 替换，而真实签名是
> `void app_loop_run(const app_loop_config_t* config) {`——替换零命中，脚本静默通过，读起来

### 19.3 E-1（P1，新）：摘抄冲账无退避

**现场**（31a C2，一次完整「存→拔→插→冲账」）：

```
95.642  boxsel: excerpt page=105 ... copy=256 truncated=0
95.644  excerpt enqueue -> 0 (pending=1)
96.259  mkdir(/sdcard/.readpico): errno=5, keeping 1 queued
96.270  sd: present=0 invalidated=1        → 96.276 关书 → 97.315 books=0
96.259 → 100.967  389 次重试（388×errno=2 + 1×errno=5），平均 12 ms 一次
100.977  Mounted APPSD ... at 324 ms
100.994  excerpt: flushed, pending=0       ← 挂载后 17 ms
```

**量化**：每次 2 行 / 127 B，389 次 = 49.4 KB / 4.708 s ≈ **10.3 KB/s = 115200 的 89%**。

**代码**（行号已核）：

| 位置 | 行为 |
|---|---|
| `main/apps/app_book.c:9259` `on_tick()` → `:9263` | 每个循环片无条件调 `excerpt_footer_tick` |
| `:1833` → `main/book/excerpt_store.c:189` | 失败只 `return EXCERPT_FLUSH_FAILED`，**不记下次时刻** |
| `excerpt_store.c:201-204` / `:206-210` | 失败即 `ESP_LOGW`，每片两行 |
| `:191` | 唯一时间判据是 `s_ready_at_ms`（挂载后 5 s），失败档不参与 |

**修法（审计批准，进 31b）**：

- 单一时间判据 `s_next_try_ms`（不许两个字段各判各的）：`notify_mounted` 写 `now+5000`（让行），
  失败写 `now + 退避档`，成功清 0。
- **退避固定三档 50 / 200 / 1000 ms，此后维持 1000 —— 无递增律。**
  （2026-10-31 审计附注 1 收口：原「`min(1000, 4×档)`」有两种读法——4× 作用于档位递进得 50/200/800，
  或视作固定三档封顶；两读并存不许进码。取固定三档，理由：值可静态断言、可入 B 牙，且与判读报告原口径一致。
  4.7 s 窗口内两读都产出个位数重试，收口不改变验收结果。此处写死一句，防第三种解读。）
- 日志：首次失败必打，每退避档各一次，成功补 `flushed after N retries (T ms)`。
  **「失败而不留痕」的钉子不动**，只降频不静音。
- **验收最小证据**（只咬两个数）：N 从 389 → 个位数、UART < 0.3 KB/s。
- **因果闭环条款**：31b 落码后复测「存→拔→插」，若「挂载→发布」回到 178 ms 档 → E-1 因果闭合，
  OPEN→CLOSED；仍 ≥800 ms → 另立新案，不许默认归因。

### 19.4 E-2（P2，新）：5 s 让行锚错对象，修码

**现场**：`Mounted` 100.977 → 队列 **100.994 就写卡**（17 ms）→ `mounted=1` 101.863 才开始计 5 s。
边沿挂在 `app_loop.c:628 if (gained) excerpt_store_notify_mounted(...)`，而 `gained` 要等状态发布。

**修码（审计批准，修注释否决）**：`read_pico_sd` 内部维护 `s_mount_epoch`，真实挂载成功处 +1，
随状态发布或独立 getter 暴露；`app_loop` 观测 epoch 变化 → 调 `notify_mounted`。

- **依赖方向钉死**：组件层不许反向调 app 层（`publish_info()` 里直接调 `excerpt_store_notify_mounted`
  是组件→app，与 push 单向依赖纪律同一族，禁止）。
- 顺带收益：epoch 变化时刻 = 挂载完成时间戳，E-1 复测不必靠日志墙钟手工对齐。

#### 19.4a 抢跑窗：epoch 边沿晚一拍会复原 E-2 现场（2026-10-31 审计附注 2）

**窗从哪来**：`s_mount_epoch` 在组件内挂载成功处 +1，若 `app_loop` 要到**下一个循环片**才消费边沿、
才 `notify_mounted` 写 now+5000，中间这一片 `excerpt_store_tick` 照常跑。而退避到期点有相位依赖：
拔卡期最后一次写退避的失败必发生在挂载成功**之前**，其 +1000 ms 到期点落在挂载后 0~1000 ms 之间。
边沿消费一旦晚于到期点，队列就在「卡已挂载、让行未写」的窗口里 mkdir 成功并冲账完成——
**这正是 100.977 挂载 / 100.994 落盘的复发形态**，会把「挂载后 5 s 内零写卡」这条正面判据打成假红。

**钉死（单片顺序，不许换位）**：`app_loop` 单片内固定

```
poll_sd（挂载发生） → epoch 观测 + notify_mounted → excerpt_store_tick
```

挂载到让行全链**同一片**，窗口归零。若挂载完成不在 poll 链上（异步探测任务自己 mount），
送审时必须注明边沿同步点落在哪一拍，不许留「下一片再说」。

> **本问已结（2026-11-01，E-2 落码批）**：答案不是「同一循环片」，是**落在写卡前一行**——
> `excerpt_footer_tick()` 首行调 `excerpt_store_mount_yield(epoch, now)`，紧邻下一行的
> `excerpt_store_tick`。同函数、相邻两行，中间**无物可插**，比「同一循环片」强一档：
> 同一片内仍可能有别的调用先跑，相邻两行没有这个缝。挂载在 `sd_probe` 任务里，poll 最早
> 下一拍才知道——所以只靠 poll 一片，窗口是「一拍」，贴在写卡前才是 **0**。详见 §13.30。

**顺带一条**：tick 首行单一判据（`s_next_try_ms`）已天然消除「让行期内失败写覆盖让行」的竞争——
让行期内 tick 直接 return，失败写没有发生路径，因此让行写入用**覆盖式**即可，无需 max 合并。
这条定了就别在实现里再加 `if (now > s_next_try_ms)` 之类的二次保护，加了反而制造第三个时间源。

### 19.5 #6b 口径改判：5 s → 10 s（并加一条正面判据）

## 二十、26.9.30 commit 3：读者句柄释放（机制二，2026-10-31）

**一句话**：提交四拍是 rename → rename → remove，读者脚下那条簇链在最后一拍回到 FAT。
修法只有一条——提交前把书**完整关掉**。「只关句柄、保留阅读态」是假修复，已否。

### 20.1 机制二（为什么 commit 2 单独出包不改善它）

### 20.3 两拍与死线（为什么不能同步等）

`prep_task_request_stop()` 最长同步等 1 s（`app_book.c:4491`）。在泵里同步等会把主循环
钉住——与 gen25 接线裁定 #1（页面不许「按下去 1 秒没反应」）同一条纪律。所以：

```
本帧：take 到请求 → release 开始；命中位 0 → app_book_request_prep_stop()（非阻塞）→ 返回 false
下帧：泵每帧都进（app_loop.c:1788 无条件调用）→ prep 已自删 s_prep_task=NULL → 关书 → run_commit
```

- 请求在泵内部 take（`app_transfer.c:1338` 起）：只有泵持有这份跨帧状态。
- 死线 = `PUSH_YIELD_WAIT_MS`（1500 ms，复用让路链同一个数，不新立第二个）。
- 越过死线 → `push_sink_commit_abort(PUSH_ERR_BUSY)`（`push_sink.c:1382`）：**不回写请求**
  （回写 = 无限重投，2 s 上界正是禁它），作废扣下的两个 UI 位，明确回 ERR(7)。
- 关书动作：`boxsel_boundary_reset` → 面板收 → 四个排期位清 → 试取绘制锁（`pdFALSE` 让出，
  `portMAX_DELAY` 禁止）→ `save_progress()` → `free_book()` → `s_view = SHELF`。
  视图必须离开 READING（`s_text` 已空），提交成功后由 `ui_post_open` 打开新书。

## 二十一、26.9.30 commit 4：四处静默闭合 + `.part` 账本 + 欠账重试（2026-10-31）

**一句话**：以前一次写失败等于整篇重传；现在先回到本包起点重写一次，再不行就把这 241 B
存进欠账槽、下次 DATA 之前补上，补不上才终止。前提是「本包起点」这个量存在——
`s_part_len` 就是它，而且必须在 ARM 成功那一刻就位。

### 21.1 四处静默（P0-2a）

| # | 位置 | 过去 | 现在 |
|---|---|---|---|
| ① | `part_put()`（`push_sink.c:546`） | `fwrite` 判了、`fflush` 没判——`f_write` 失败仍返回 true，后续包静默写到错位 | `fflush` 返回值必判，失败即「位置已脏」，交 `part_append` 的 rewind 链处理 |
| ② | `:1366` | append 失败只 `reply_err`，设备端零留痕 | `append seq=%u errno=%d, %u B lost at offset %u`（四要素：哪一包、什么错、丢多少、丢在哪） |
| ③ | `:1390` | 检查点 `(void)part_sync()` | `if (!part_sync()) ESP_LOGW("checkpoint sync failed, errno=%d")` |
| ④ | `:1318` | `part_open_fresh` 失败零日志 | `part open(%s) errno=%d` |

**①必须与②③同批**：单上①会把「以前推得完」变成「推到一半回 ERR」——观感倒退。
现在①的失败先被 rewind 救一次、再被欠账槽接住，真要上报时才算真失败。

### 21.2 `.part` 账本与欠账槽

**不变式（改写后，时点提前到 ARM 时刻）**：

> `.part` 的可见长度、`s_part_len`、以及「下一包应写到的位置」三者，从 **ARM 成功那一刻**起恒等；
> 任一时刻允许的偏差只有「文件比账本短」（此时不许 rewind，只能按 `s_part_len` 补齐或终止）。

原表述是「进入欠账态时三者相等」——那是这条的推论，漏掉了 **enter 之前** 的整段。

**起点两处（这是整个机制的地基）**：

| 位置 | 赋值 | 缺了它会怎样 |
|---|---|---|
| `try_adopt()`（`:2393`） | `s_part_len = nv.received` | 续传会话首包写失败 → `part_rewind()` 按 0 截断 → NVS 锚定的 10,000 B 整段抹掉，本会话内无人能救（VERIFY 只拦坏文件，救不回续传链） |
| `PUSH_ACT_READY` 分支（`:1328`） | `s_part_len = 0`（连同欠账槽清零） | 「wb」已把文件截到 0，账本留着旧长度 → 第一次 rewind 把文件延长成 0 填充 |

**rewind 三步**（`part_rewind()`，`:530`）：先放句柄（FS_LOCK=0 禁止同文件双开，`truncate()` 走 VFS 会自己再开一遍）
→ `truncate(s_part_len)` 判返回值 → 重开 `"ab"`（append 位置由目录项 size 决定，truncate 改的就是它）。

**`part_append()` 返回值语义**（`:558`）：`true` = 数据已保住（在盘上或在欠账槽）；`false` = 没接住。
调用方（`:1355`）不变——「一次写失败」不再自动等于「整篇重传」。

**`drain_owed()`（`:581`）两个调用点**：DATA 分支入口（`:1355`，先补欠账再收新包）、END 之前（`:2110`）。
两处返回 false 都走既有分支：`CANCEL + ERR(5)`，不新增错误码。

**为什么 drain 里不 rewind**：会话要结束了，截到「本包起点」没有意义——续传锚是 NVS 记账（每 64 包一次，更旧），
下次 ARM 的 `try_adopt` 会按它截断。但句柄必须关：`CANCEL` 走 `goto_idle` 只回 `ADV_OFF`、不 `part_discard`，
句柄会跨会话残留，而 `try_adopt` 的 truncate 要求文件没被打开。

**`part_discard()` 连带清账**（`:614`）：文件删了账本必须一起归零，否则下一个会话按旧长度 truncate，补出 0 填充。
