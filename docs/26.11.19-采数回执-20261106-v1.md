### 四、锚 ① **闭合**（v1.3，2026-11-06 15:35；**长度修正等价复算**）

现场回读截图到账。截图逐字：`Read 4218448 bytes from 0x00010000 in 34.8 seconds`，
`certutil -hashfile` 得 `53c1ef93898d4e50f60dbb43f9f0d81d45bd258d762a644cc5d3980dd85498a5`；
目录 `D:\Python\pico\read-pico-20261106-5e6f8a89e039`，设备 ESP32-S3 (QFN56) rev v0.2 / USB-Serial/JTAG / MAC `14:c1:9f:d0:78:24`。

**这个哈希不等于 `5e6f8a89e039…`，但不是刷错包**。复算（本地主包，可重跑）：

```
len(Read_Pico.bin)            = 4,216,784 B   sha256 = 5e6f8a89e0398ca4…e7ffc
截图读回长度                  = 4,218,448 B   多出 1,664 B (0x680)
sha256(主包 + 0xFF × 1664)    = 53c1ef93898d4e50f60dbb43f9f0d81d45bd258d762a644cc5d3980dd85498a5
                                        ↑ 与截图哈希逐字节命中
sha256(主包 + 0x00 × 1664)    = ee2317a9…    （不命中）
```

⇒ **回读文件 = 完整主包 + 1,664 B 擦除态（0xFF）**，`0x10000` 起前 4,216,784 B **与交付包完全一致**。
在 SHA256 抗碰撞下，任一字节不同都不可能命中这次模拟值 ⇒ **设备里跑的就是 `5e6f8a89e039` 这一颗**。
多出的 1,664 B 来自手动 esptool 的长度参数（脚本 `readback.sh:21` 的 `SIZE=4216784` 是对的；本次现场用的是手动 `esptool` + `certutil`，非脚本），
参数来源不明，但**不影响结论**——尾部是擦除区，不是内容。

> **锚 ① 的值仍写 `5e6f8a89e039`（12 位）**，**不是** `53c1ef93898d`。后者是「含尾部擦除区的整块哈希」，
> 只作旁证材料。若把它当锚 ① 写进现场单，就会重演「同一实体第二真相、将来 grep 对不上」那条错法。
> 六件套 ① 由此从「我以为刷的是这颗」变成「**回读验证过的这颗**」，§3.0-e 的第九行终验**实质完成**。

**标准形态可补跑，但非必需**：`sh readback.sh COM7` 会用正确长度 `4,216,784 B` 直接产出 `5e6f8a89e039…`。
