## 一、盘什么

三个问题，逐页问一遍：

1. **谁画**：状态栏那片像素由哪一处 `ui_nav_status()` 调用画出；
2. **谁让它变新**：哪个节拍在驱动重绘（页面自己的 `on_tick`？主循环的 `nav_watch`？没有？）；
3. **谁说了算**：同一页若有两个驱动源，它们的矩形是否相交、同拍会不会各刷一次。

收口判据沿用批前的说法：**每页单调度器**。

## 三、七个发现（写码前必须知道，否则必踩）

### 发现 1：缺陷面比那一格大得多（断言级）

12 个页面里只有 2 个有分钟驱动。书架、文件管理、设备设置、传书、图片、目录、AI 阅读器、开机恢复
——**8 个页面的状态栏时钟是停的**，其中 6 个连电量也不跟（`status_bar_bg` 返回 `-1`，`nav_watch` 不刷）。

这不是本批要一次修完的范围问题，而是**首刀边界的依据**：若首刀只开书架，等于先修「被看见的那一格」，
其余七页仍停着。这个取舍必须显式写在批的边界里，不能让人以为「修完书架就没这问题了」。

### 发现 2：分钟支有两个必踩的坑，都在类型上（断言级）

`ui_nav_clock_minute()`（`ui_nav.c:159`）：

```c
int64_t ui_nav_clock_minute(void) {
    time_t now = status_time();
    return now >= 1704067200 ? (int64_t)now / 60 : -1;   // 未对时 = -1
}
```

- **坑 A（哨兵）**：未对时返回 `-1`。分钟支如果写成「`minute != shown` 就刷」，而 `shown` 的初值
  是 `NAV_WATCH_UNKNOWN(-2)`，首帧会走「未知 → 只登记」分支、把 `-1` commit 进去，之后 `-1 == -1`
  不刷——**这条路径是安全的，但只因为它恰好有 UNKNOWN 分支**。若谁把分钟支写成独立判断、绕开
  UNKNOWN，`-1` 就会被当成一个正常分钟值参与比较；更要紧的是**对时那一刻**（`-1 → 29600000`）会
  产生一次真实跳变，方向是对的（该刷），但如果 `-1` 被画成了 `--:--`，这次跳变就该刷，逻辑上必须
  允许。结论：`-1` 必须走与真实分钟**同一套** UNKNOWN/首帧语义，不许另开一路。
- **坑 B（宽度）**：分钟是 **epoch 分钟 ≈ 2.96×10⁷**。现有 `nav_watch_t.shown_percent` 是 `int16_t`
  （因为百分比 0–100 够用）。把分钟塞进 `int16_t` 会截断成低 16 位——相邻分钟仍能比较（低 16 位逐分 +1），
  但**每 65,536 分钟（≈45.5 天）回绕一次会误判一次**。字段类型必须是 `int32_t`（或 `int64_t`，
  但 32 位足够覆盖到公元 6000 年，选 `int32_t` 并把理由写在注释里）。

**这两个坑只有盘点能看出来，写码时看到 `-1` 和 `int64_t` 也不会立刻想到。**

### 发现 3：条带高度有三个数，而「整条」那个数现在拿不到（断言级）

| 数 | 值 | 出处 | 含义 |
|---|---|---|---|
| 内容实际占用 | y ≈ 18–60 | `ui_nav.c:180` 中心线 40、`UI_STATUS_TIME_PX` 28 px、电池 `y=24..52` | 画了什么 |
| 阅读器整条刷 | `{0,0,684,80}` | `app_book.c:5054` `reader_status_area()` | 阅读器认为的「整条」 |
| 手势领地 | `{0,0,684,88}` | `home_gesture.h` `HOME_RESERVED_INFO` | 不许长按开传书页的带 |

**问题**：`reader_status_area()` 是 `app_book.c` 的 `static` 函数，`app_loop.c` 的 `nav_watch` 拿不到。
要按批前口径「复用 `{0,0,684,80}`、不再声明一份」，就得把它**提权成共享常量**
（`ui_kit.h` 或 `ui_nav_layout.h`），`app_book.c` 改为引用。这是一次跨文件改动，
**不属于「只改 app_loop + nav_watch」的小切口**，必须提前申报。

**附带一笔**：整条刷用 80、手势领地用 88，差的 8 px 是空白（无内容）。整条刷不覆盖 80–88
不会留残影（那里本来就没画东西），但审计时会被问「为什么两个数」，所以要在注释里写明
「80 = 绘制范围，88 = 手势领地，前者是后者的子集且不变量」。

### 发现 4：`nav_watch_t` 必然变大，段账不再是 Δ0（推理级，按类型算）

现有 8 B：`int16_t shown_percent` + `bool shown_charging` + `bool pending` + `uint32_t pending_since`
（2+1+1 填满首个 4 B 字 + 4 B）。加分钟支至少多 `int32_t shown_minute`（4 B），
若再加一个分钟侧的 pending 标志则再多 4 B。

- 只加 `int32_t shown_minute`：8 → 12 B，**12 B 是 4 的倍数，不需要对齐跳档**，段增 12；
- 若沿用同一 `pending` 表示两个源的挂起（不推荐，语义会糊）：仍 12 B；
- 若另开 `minute_pending` + `minute_pending_since`：8 → 16 B。

**预算要提前写死**：建议 **+12 B 或 +16 B，明确申报，不再指望填隙**。上一批 `s_dual_seq` 落进
3 B 空隙是运气，不是方法；这一批尺寸可算，就直接算准。

### 发现 5：整页重绘与账不同步，冗余刷是**空差分 no-op**（断言级再走一层）

`nav_watch` 的账只在两处更新：首帧 UNKNOWN 分支、上屏成功后的 commit。**页面自己的整页重绘
（进书架、翻页、切页回来）不走这两处**，但账上的值没有被污染——因为整页重绘用的也是同一个
`pmu_battery_percent()` 与同一个 `ui_nav_clock_minute()`，画出来的与账上同源。

加分钟支后仍是同源；成本是：整页重绘刚画了新分钟，账上还停在旧分钟，下一拍判「分钟变了」→
再刷一次整条。**但这一刷落在差分上等于不存在**（2026-11-05 审计细化）：

> 整页重绘已把条带画成新分钟 → `nav_watch` 补的那一刷，fb 内容与屏上一致 → **差分空集 →
> 包围盒为空 → 驱动层跳过**。差分粒度是像素，闪的粒度是包围盒（26.11.7 原话），
> **空差分没有盒**。

所以预期观感是**无感**，成本只剩「一次比较 + 一次被跳过的 EPD 调用」。真机验证点随之改写：
**进书架后条带不应有可见闪**；若可见，说明差分链路有第二真相，回头查那里——不是接受一个已知闪。

处置：仍不同步账（跨过去就要页面知道 `nav_watch`，正是本批要避免的耦合）。

### 发现 6：触摸守卫会把分钟推迟到松手（断言级，与阅读器同构）

`nav_battery_watch()` 的守卫：`overlay || consumed || pressed || released || touch->touched` → 直接返回。
阅读器侧 `reader_clock_tick()` 的守卫是 `ctx->touch && ctx->touch->touched` → 返回。

两者同构：**用户连续翻页时时钟不更新，松手后补一次**。这是正确行为（不打断手势），
但要写进判据——否则「翻页时时钟停着不走」会被读成 bug。

### 发现 7：便车债追到根了——`poll()` 挂在按键读取的首句上（断言级，**节拍数已修正**）

> **修正记录（2026-11-05，审计抓出 40 倍偏差）。** 本节初版写「每拍调、5 ms 一次 I2C 读」，
> 错。原因很具体：我引了 `app_loop.c:1843` 那**一行**，却没引包着它的 `if`（`:1839-1842`）——
> **把调用行从外层门里剥出来读，正是 26.11.16 判据 6 第二层那次的同一个失效形态**，
> 第二次出现。断言级与断言级打架时，唯一裁判是原件：`grep -n "take_key_action" main/`。

**全仓只有一个调用点**（`main/lock_screen.c:120` 那次是锁屏自己的 40 ms 链，独立）：

```c
// app_loop.c:1839-1843
if (quick_lock_requested || (read_pico_pmu_ready() && !current->holds_pmu && !usb_storage_active()
    && ctx.now_ms - last_lock_poll_ms >= APP_LOCK_POLL_MS)) {   // APP_LOCK_POLL_MS = 200
    last_lock_poll_ms = ctx.now_ms;
    ... read_pico_pmu_take_key_action();
```

所以常态节拍是 **200 ms 一次（5 读/秒）**，与电量判定 v2 §3.1 的结论一致；`poll()` 内部
无节流这一条仍成立（`read_pico_pmu_poll()` = `refresh_core(false)`，`read_pico_pmu.c:650`），
只是外层门把它限到了 200 ms。

**债的准确形态变了**（这才是修正后该记的）：

> 电量采样的节拍 = **锁屏键轮询的节拍**，且被 `read_pico_pmu_ready()` / `!holds_pmu` /
> `!usb_storage_active()` 三重门控。谁调 `APP_LOCK_POLL_MS`（哪怕是为了省电改成 500），
> 电量跟着变慢；谁在某个页面置 `holds_pmu`，该页电量就是冻的。

**另一条同源事实**：全仓只有 `app_key.c` 与 `app_selftest.c` 置 `holds_pmu = true`——这两页
不 poll、快照停，但它们 `status_bar_bg` 都是 `-1`，`nav_watch` 本来就不跑，**不影响本批**；
将来若给它们开 bg，先得解掉 holds_pmu。

**处置（审计裁定第 4 项）：只记账。** 解耦独立批，前置两件：① 调用点普查（本节已完成）；
② 按键时延真值表——解耦后 `take_key_action` 只读 FIFO，按键响应路径不得退化，那是解耦批
自己的主判据。节拍批只拿走「债根已定位」这一格。

## 四、首刀切口建议（待批，不落码）

按批前口径「最小切口 + 矩形跟触发走」，落成这样：

| 项 | 内容 |
|---|---|
| 改动面 | `nav_status_watch.{h,c}` 扩分钟支；`app_loop.c` 的 `nav_battery_watch` 扩一分钟源与一个矩形选择；`app_book.c` 的 `reader_status_area` 提权为共享常量（其余不动） |
| 分钟支开启条件 | **只有书架**：`status_bar_bg(ctx) == 0xE0/0xF0` 已经在回答「这一页要不要管」，但首页也返回 `0xFF`。需要一个「这一页有没有自己的分钟节拍」的答案——建议加一个 `app_desc_t` 字段（`bool self_clock_tick`），首页/阅读器置 true，其余 false → 默认 false 即「nav_watch 管」，**新增页面自动获得分钟节拍**，这是比白名单更好的默认值 |
| 矩形 | 分钟变 → `{0,0,684,80}`（整条）；电量变 → 保持 `{520,24,136,32}`；同拍都变 → 整条（它包含电量区，并集即整条），**commit 提交全部当前值** |
| 守卫 | 沿用现有的 overlay/touch/consumed 五条，不加新条件 |
| 账 | `nav_watch_t` 8 → 12 B（`int32_t shown_minute`），段账**申报 +12，不指望填隙** |
| 测试 | 现有 12 组真值表扩分钟支（至少：整点跳变、-1 哨兵、touch 期间不刷松手补、同拍双变一次刷、整页重绘后冗余一次、跨天后日期不误判） |

**关于 `self_clock_tick` 这个字段**（**已批，plain bool**）：本批唯一新增的 `app_desc_t` 字段，
缺省 `false` = 「这一页没有自己的分钟节拍，`nav_watch` 管」。首页必须显式置 `true`，否则
ROOT 会出现双调度器重叠（整条 80 含时钟区 156×44）。结构牙咬这一条。

**首刀边界已裁：只开书架**，且纠一笔——初版说「一步到位改动面不变」**不成立**。7 个页面
（文件管理 / 设置 / 传书 / 图片 / 目录 / AI / 开机恢复）的 `status_bar_bg` 全是 `-1`，
点亮它们的前提是**逐页实现 bg 回调 + 逐页真机验底色**（电量批教训：底色错一档 = 色斑）。
一步到位的真实代价是 7 份底色判定 + 7 页真机观察。**盘点的价值（通例入账、边界显式化）已经拿到；
点亮是后续批，底色成熟一个开一个。**

## 六、这份盘点没覆盖的

- **真机行为**：整条刷 `{0,0,684,80}` 在书架上的实际观感（是否有可见闪、GL16 残影），本盘点不含；
- **`ui_nav_status()` 在图标的网络/蓝牙查询上是否有耗时**（每刷一次调一次
  `read_pico_transfer_get_status()`，`ui_nav.c:185`）——分钟级刷新下这是每分钟一次，可接受，
  但没实测；
- **锁屏 / 熄屏路径**的状态栏（`lock_screen.c` 自带 `read_pico_pmu_poll()` 40 ms 节流，
  与主循环是两条独立链，未盘）。
