## 二、读码三问（断言级）

### 2.1 Q1 FIFO 语义

| 项 | 事实 | 出处 |
|---|---|---|
| 深度 | **8**（主机侧循环上限同值） | `read_pico_pmu_protocol.h:27` `PMU_EVENT_FIFO_DEPTH 8` |
| 取出方式 | `EVENT_COUNT` 读计数 → `EVENT_PEEK` 读一条 → `EVENT_ACK` 消一条 | `refresh_core`（`:624-631`）、`take_key_action`（`:397-412`） |
| 溢出策略 | **PMU 固件侧**：「满时先丢 INFO，再丢 NOTICE」 | `docs/llms-full_zh_cn.md:129` |
| 按键 severity | **本仓不可见**（`pmu_event` 结构只有 `arg0/arg1`） | 同上结构定义 vs `read_pico_pmu.c` 解析 |
| 200 ms 门裹什么 | **整个取键动作**（条件体第一行调用） | `app_loop.c:1855-1858` |
| `ack` 的代价 | 内部 `vTaskDelay(pdMS_TO_TICKS(10))` + 一次 `poll()` | `:371-381` |

**两层不混（v2 新增，这是 K2b 的前提）**：

- **窥视**（PEEK）只把事件写进 `s_snap.event`，**不动 FIFO**——`refresh_core` 就是窥视者；
- **消费**（ACK）把事件从 PMU 侧移除——只有 ACK 才是消费。

上一版把 `refresh_core` 的事件循环也算作「消费点」，是把窥视当消费。**危害同构但修复不同**：
消费双真相 = 事件被两个消费者抢；视图双真相 = 两个消费者读到不同事件。

**两条判据前提**：

1. **现状键读取节拍就是 200 ms**——基线，不是缺陷；K3 的对照从它起算。
2. **「按键会不会被 FIFO 丢掉」仍是未定项**：severity 未确认前，K4 只断言「已入 FIFO 的事件被正确处理」，
   不断言「一定入得了 FIFO」。这一句进 instrumented 采数清单（§5）。

### 2.2 Q2 门的三重条件 —— **v2 重写：门谓词单源化**

现状原文（`app_loop.c:1855-1857`）：

```c
if (quick_lock_requested || (read_pico_pmu_ready() && !current->holds_pmu && !usb_storage_active()
    && ctx.now_ms - last_lock_poll_ms >= APP_LOCK_POLL_MS)) {
    last_lock_poll_ms = ctx.now_ms;
```

**上一版归属表作废**。作废理由逐条记账（审计打回的三项，此处**显式放弃**，不申报为变更）：

| 被夹带的变更 | 现状 | 「按键侧无条件取」后 | 处置 |
|---|---|---|---|
| `holds_pmu` 期间按键 | **死**（门挡住整段） | 活，且在升级/自检序列里插 I2C 流量（每次 ≥10 ms 任务延迟） | **放弃**：独占窗口最不能容忍额外总线活动，不拍脑袋接受 |
| `usb_storage` 期间按键 | **死**（总线让出） | 活，违反既有窗口约定 | **放弃** |
| 键响应时延 | ≈200 ms（门内） | ≈一拍（5 ms） | **放弃**：改善也是变更；本批不以键时延为优化目标，要改单独立号 |

**原方案的动机也不成立**：表中「页面退出后键要等 200 ms 才活」是误读——门是「到点才取」，
不是「错过窗口永不取」，200 ms 键节拍就是基线（本回执自己写着「不改 `APP_LOCK_POLL_MS`」）。
动机不成立，设计就站不住。

**替代方案：把门变成单源，而不是把门划给一边。**

四条门的本质是「PMU 总线使用权」，采样与取键都要总线，就该调同一份谓词：

```c
// 拟增 main/app/pmu_bus.h —— 纯谓词头，不 include 任何 esp_*
typedef struct {
    int64_t last_key_ms;      // 取键自己的戳
    int64_t last_sample_ms;   // 采样自己的戳
} pmu_bus_clock_t;

bool pmu_bus_static_ok(bool pmu_ready, bool holds_pmu, bool usb_active); // 三条件单源
bool pmu_bus_due(int64_t last_ms, int64_t now_ms);                       // 时间维，戳由调用方自持
```

主体（落码批才写，此处只定形）：

```c
// 短路支必须显式写出来，不能靠 || 的副作用（这是两戳分离的第一个咬点）
if (quick_lock_requested) {
    clk.last_key_ms = ctx.now_ms;      // 只推 key 戳：短路绕过的正是「取键」
    key_action = READ_PICO_PMU_KEY_SHORT;
} else if (pmu_bus_static_ok(read_pico_pmu_ready(), current->holds_pmu, usb_storage_active())) {
    if (pmu_bus_due(clk.last_sample_ms, ctx.now_ms)) {
        clk.last_sample_ms = ctx.now_ms;
        read_pico_pmu_poll();                       // 采样：让值新鲜
    }
    if (pmu_bus_due(clk.last_key_ms, ctx.now_ms)) {
        clk.last_key_ms = ctx.now_ms;
        key_action = read_pico_pmu_take_key_action();  // 取键：纯 FIFO 读
    }
}
```

**解耦本体由此只剩一件事**：`take_key_action` 瘦身为纯 FIFO 读，`refresh_core` 从按键路径摘出，
采样立自己的 200 ms 节拍与属主。**行为零变更**——三条静态门两侧同效、200 ms 节拍不变。

**债照解**：债的病根是「采样寄生在按键动作里」（值的新鲜度取决于有没有人取键），
不是「两者共用门」。共用门是对的——它们共用总线。

**结构守卫（v2 新增，两戳分离）**：

- `last_key_ms` 与 `last_sample_ms` 必须是两个独立变量/字段，**禁止共用一个戳**；
- **第一个咬点**：`quick_lock_requested` 短路时现状会推进 `last_lock_poll_ms` 但**不取 FIFO**。
  解耦后这一推进只能落在 **`last_key_ms`** 上——若误写到 `last_sample_ms`，采样被推迟 200 ms，
  K1 直接变红。这正是两戳分离最容易被写错的地方，守卫要咬它。
- **不要平移旧陷阱**：现状 `last_lock_poll_ms` 在条件体内**无条件更新**（`:1857`）。

### 2.3 Q3 分发路径

- `take_key_action` → 单个 `read_pico_pmu_key_action_t` → **`app_loop` 同体内直接处理**，**没有二次入队**；
- 时延账算到「动作开始执行」：体内第一行 `last_input_ms = ctx.now_ms` 即分发点；
- **折叠语义**（K4 的根）：`KEY_SHORT` 只在 `action == NONE` 时赋值；`KEY_LONG` 无条件覆盖。
  同批里 **LONG 吞掉所有 SHORT**，多个 SHORT 只留一个，**但全部 ACK**。
- 现状 `KEY_SHORT` 分支已 `ESP_LOGI("KEY_SHORT id=%u held=%u", id, arg0)`——**第一个 SHORT 的 arg0
  已经在日志里**，只是没有返回给调用方。这是 K4 载荷断言可以低成本落地的原因（§3.1）。

## 三、K 组定稿

### 3.1 正例（新行为，空壳即红）

| 组 | 定稿断言 | 层 | 红来源（刀） |
|---|---|---|---|
| **K1** | **不产生任何按键事件**时，`percent/charging` 仍每 200 ms 更新（快照 `generation`/时间戳推进）；**且 `quick_lock_requested` 短路不推迟采样** | 断言级（宿主） | V-A 摘采样支 |
| **K2a** | 一次取键把 FIFO 取空（`pending_events → 0`），**取键路径 `refresh_core` 调用计数 == 0**（允许直读 COUNT/PEEK/ACK） | 断言级（宿主计数） | V-B 把 `refresh_core` 塞回取键路径 |
| **K2b** | **FIFO 动点行 == 9**（组件内 5 + `main/apps` 3 + `main/factory` 1）；归属点 8 为人读注脚。解耦不新增、不转移；`refresh_core` 的 COUNT/PEEK **不 ACK**（窥视非消费） | **结构级（源码守卫）** | V-F 在 `refresh_core` 里加一条 ACK |
| **K3** | 短按时延 **≤ 基线 max**（instrumented bin 实测 P50/P95/max，纪律 19，先测后钉）；**上界数值本身待测**（纪律 20 ①类登记，见 §3.4）；**宿主合成时间步进单位是微秒**，K 组沿用 D 组同桩时先查（D 组踩过 `100` vs `100000`） | 断言级 | V-C 放宽上界 |
| **K4** | ① 3 连按 = **1 分发**（现状保真）；② FIFO **清空**；③ **LONG 覆盖 SHORT**；④ **分发载荷 == 批内第一个 SHORT 的 `arg0`**（**宿主禁传 NULL**，见 §8） | 断言级 | V-D 取一即返不 ACK；**V-E 深度折 1**（由 ④ 咬住） |

**K4 ④ 的接口代价（显式申报）**：`take_key_action` 需加一个可选 out 参数
（`uint16_t *held_out`，可 NULL），带出第一个 SHORT 的 `arg0`。**接口扩参、行为零变更**——
现状日志已携带同值，只是不外露。若不接受扩参，则 V-E 无门（深度折 1 与深度 8 在 ①②③ 下
完全不可区分：存最后一个、分发一次、COUNT 归零、载荷同为 SHORT）。

**K2 拆层的理由**：`refresh_core` 调用计数是**行为事实**（宿主可数），消费点清单是**源码结构**
（守卫可 grep）。两层证据不能互相替身——这是 S1 那条「判据在能拿到它的那一层拿」的第二次应用。

### 3.2 回归（断言「不变」，红由刀代供）

> **v7 补 K6.1 的理由**：PIN 环每 40 ms 调 `take_key_action`，而 `take` 的循环首句是 `read_pico_pmu_poll()`

> 摘 `poll` 之后它停：这是解耦的**直接副作用**，不是意外。本行把它**升为条目**，理由是它有具体验收面
> （PIN 键可退出），不是一句设计注。

#### 3.2-a 便车有两处座位，范围格写死（v8 补，审计裁决）

**「采样搭按键动作便车」不是一处，是两处**：

| 座位 | 位置 | 谁在搭 | 解耦后 |
|---|---|---|---|
| **一** | `take_key_action` 循环首句 `read_pico_pmu_poll()` | 取键路径 | **摘除**（K2a：取键路径 `refresh_core` 计数 == 0） |
| **二** | `drain_events()` 内的 `poll()`（`read_pico_pmu.c:385`） | **锁屏静默环**（20 ms，`sleep.c:158-179`）、PIN 环退出后的 drain | **默认同批摘除** |

**范围格写死这一句**：**`drain` 的 `poll` 属便车面，默认同批摘除。**
支撑：消费面 grep 零命中（`lock_screen.c` / `ui_pinpad.c` 无 `read_pico_pmu_get`）⇒ 摘除**今天行为中性**。
**若只写「`take` 纯 FIFO 读」，债在锁屏链上还剩半条**——静默环与 PIN 环的 drain 照旧载着采样跑，
账面会变成「摘了一半说摘完了」。

**由此推出的第一受害者（「待穷举」升格为「机制已知、必须测」）**：

| 项 | 内容 |
|---|---|
| 机制 | **解耦后**锁屏期间 `s_snap` 冻结（两处便车都断）⇒ **解锁首帧若读 `s_snap`，显示的是入锁时刻的电量**，直到主循环 200 ms 门首次采样。**（解耦前不冻结，见下「两格已关」③）** |
| 候选点 | **v10 读码更正**：~~`app_home.c:313` 是「回前台首帧读 pmu」~~ → 它是**概览状态页**的「电池 Battery」行（`draw_status_page` → `read_pico_pmu_get()` → `&s_snap`）；**状态栏电量在 `ui_nav.c:178 → :189`**（`ui_nav_status` → `pmu_battery_percent(pmu)`）。**两处都读 `s_snap`，仓内无第二源**（详下「两格已关」） |
| 升格理由 | 不再是「可能有」，而是**两条已证事实的必然拼接**：采样只由主循环发生 + 首帧先于首次采样 |
| 验收 | **「解锁首帧电量新鲜度」对表**：入锁时记电量 → 锁屏静置 ≥ 3 min → 解锁，首帧显示值与真实值（PMU 调试页或二次唤醒后读数）比对。**v10 增补前基线**：W1 十轮顺手记两列（协议 §2.1-b），解耦前形态先钉住 |
| 分级 | 若首帧只是「慢一拍」，记 P2（可接受，K8b 同族）；若显示**入锁时刻的旧值且不再刷新**，记 P1 |

**两格已关（v10，2026-11-06 刷机前，逐条读码）**：

| 格 | 问题 | 结论 | 端点 |
|---|---|---|---|
| ① | `app_home.c:313` 是否消费 `s_snap` | **是**，但**位置需更正**：`read_pico_pmu_get()` 返回 `&s_snap`（指针，零拷贝），该行属**概览状态页**；状态栏电量另有其点 | `app_home.c:313` / `read_pico_pmu.c:747-749` / `ui_nav.c:178,189` |
| ② | 唤醒首帧电量读 `pmu_battery_percent()`（`s_snap`）还是直读 I2C | **读 `s_snap`**。`pmu_battery_percent` 是 header 内 `static inline`，形参只有 `const pmu_snapshot_t*`，**没有 I2C 分支**；渲染路径内无 `refresh` / `poll` 调用。唯一例外 `app_home.c:428` 是概览页 `on_enter`，而 **`on_enter` 只在切页 / 启动 / 菜单返回时调**（`app_loop.c:484 / 1237 / 2183`），**解锁回前台不切页** ⇒ 不覆盖首帧 | `read_pico_pmu.h:131-145` / `ui_nav.c:189` / `app_loop.c:484,1237,2183` |
| ③ | **两列的物理前提**（v10 自补，不问就不成立） | **`poll()` 就刷电量**：`refresh_core(false)` 含 `QUICK_BATTERY` → `parse_quick` → `qb_soc`/`quick_ok`（`:621-623`）。所以「采样」与「电量新鲜」是**同一件事**，不存在「刷了事件没刷电量」的中间态 | `read_pico_pmu.c:585-652` |
| ④ | **形态前提**（同上） | **PIN 盘不画电量**（`ui_pinpad.c` 对 `percent`/`battery` 零命中）⇒ 有 PIN 时「唤醒首帧」**没有那两列可读**，取数点必须改到「解锁后首个含状态栏的主页面帧」 | `ui_pinpad.c` 全文 |

> **② 的连带推论，比 ② 本身重要**：首帧新鲜度**不依赖 20/40 ms 环**。
> 解锁成功路径显式调用 `drain_events()`（`lock_screen.c:134`），而它**首句就是 `poll()`**（`:385`，队列空也走一次）
> ⇒ 解锁瞬间快照必然新过一次。**解耦后首帧冻不冻，取决于 `:134` 那一句留不留，不取决于环。**
> 这条把 P1 的成立条件从「未知」收到**一行代码**上——解耦批裁决时只需回答「`drain` 的 poll 摘不摘」，
> 而回执 §3.2-a 已写死「**默认同批摘除**」⇒ **P1 的默认结局是「成立」**，除非另行裁决豁免 `:134`。


**正面效应清单加一行（可复算的数）**：`take_key_action` 摘掉 `poll` 的 **5 条事务**
（IDENTITY / STATUS / QUICK_BATTERY / EVENT_COUNT / EVENT_PEEK）⇒ **PIN 期间总线频率下降**
（现约 50 Hz = 40 ms 环两次 poll ⇒ 摘后约 25 Hz 量级，按每拍一次事务组计）。
**这不是「零变更」，是申报过的改善**（Q2 框架：改善也是变更，走同一条申报）。

**K8 二分不许混写**：发现 5 的「冗余刷」画的是**同值**、空差分、无感；K8b 画的是**新值**，
是真实内容更新。两类形态相近、性质相反，混写会导致「值变了却判 FAIL」。

**K9.1 的连带效应（风险 3 与 K6 串行备注消解；风险 1 有一条例外，见下）**：

| 原风险 | 在同任务形态下 |

## 八、落码说明（三条写死，不许自由裁量）

### 8.1 K4：宿主测试里 out 参数禁止传 NULL

`held_out` 的 NULL 容忍是给**既有调用点**的零改动通道（`app_loop` 现有两处），**不是给测试的**。
宿主里传 NULL 等于自动放弃载荷断言——**V-E 的门就白装了**：深度折 1 会 SURVIVED，
而没人知道为什么（因为门根本没接上）。

### 8.2 K2b：「窥视不是消费」的对称判据

`refresh_core` 保留 PEEK 循环**不违反**消费权单源——视图与消费是两个资源。但对称的判据是：

> **PEEK 循环内一旦出现任何状态推进**（局部缓存、计数、标志位更新），它就**升级为消费者**，
> 动点清单 +1，守卫红。

这一条防的是「我只是加个缓存」式滑坡：缓存就是视图的第二真相，和 ACK 一样会抢事件。

**守卫形态（v3 定稿：按行比对，不留解释空间）**：

```bash
# 期望：总行 9（组件内 5 + main/apps 3 + main/factory 1）
grep -rn "read_pico_pmu_event_ack(" --include=*.c main/ components/ \
  | grep -v "esp_err_t read_pico_pmu_event_ack"        # 期望 7
grep -rn "PMU_CMD_EVENTS_CLEAR_ALL" --include=*.c main/ components/   # 期望 2
```

断言三件：**总行 9**、**7 ACK / 2 CLEAR 之分**、**目录分布 5+3+1**。
不断言行号（会漂）；「8 个归属点」只作人读注脚——**守卫的单位是行，账面必须写明选了哪个单位**
（纪律 21 在本批的第二次适用：行与点是两个层面）。

**新增动点 = 守卫红 = 到期通知**，与结构牙同机制：红了不是「坏了」，是「这里有新东西，请裁决」。

**首日红是设计内的（写进落码批预期管理）**：`take_key_action` 瘦身当天，动点形态必变
（它自己读 COUNT/PEEK/ACK，行数会重排），守卫**按设计红**。重定基线走同一要件：
新的 9 行（或裁决后的新数）清单 + 可复算命令 + 每行归属点标注。
**开批第一天有人把这条红当回归误报，是这句话要防的。**

三次漏数的根因是**记忆按主循环视角组织**，不是「下次小心」能解的——只有守卫能解。

### 8.3 Q2：状态不许串写

| 守卫 | 判据 |
|---|---|
| 门谓词不许分裂 | `pmu_bus_static_ok()` 三条件单源，采样/取键两侧同调一份 |
| **状态不许串写** | `last_sample_ms` 只许出现在采样侧、`last_key_ms` 只许出现在按键侧（grep 可查） |

两条是同一纪律的两个方向：**结构不许分叉，状态不许串写**。
`quick_lock_requested` 短路支单独成段、禁 `||` 副作用——已确认。

### 8.4 K3 阈值未填期间：宿主用例不得静默跳过

K3 的阈值要到 instrumented 基线才落地，落码期会出现「断言结构已写、数值还没填」的中间态。
这个中间态**允许存在，不允许静默**：

| 要求 | 内容 |
|---|---|
| 不得静默跳过 | 用例必须**打显式日志**（如 `K3 pending: threshold unfilled, skipped`），日志进测试输出 |
| 台账可见 | 跳过状态写进落码批回执的「判据缺口」栏，一行一条 |
| 跳过 ≠ 通过 | 汇总行里 K3 记 `PENDING`，不进 PASS 计数——**不能因为「跑了没红」就记绿** |

依据：**S2 那条纪律在测试侧的形态**——否定性观测与「没跑」都不能冒充「跑过且通过」。
静默跳过是最廉价的自我欺骗：它让测试报告看起来完整，却把唯一的证据位空着。
